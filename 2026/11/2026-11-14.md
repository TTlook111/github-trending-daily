📖 项目是干什么的

这是 Modern Web Guidance 的**源码仓库**，真正的产物是 `GoogleChrome/modern-web-guidance` 那套技能。它要解决的问题很具体：LLM 的训练数据里堆满旧代码，导致 Agent 总爱用臃肿的 JavaScript 去实现浏览器早已经原生支持的能力；即便模型知道某个 API 存在，也缺乏生产可用的现代写法密度。这套技能就是把浏览器厂商的权威知识，直接注入到编码 Agent 的上下文里。

机制上有四个 CLI 入口：`install` 交互式安装、`search` 检索相关指南、`retrieve` 按 ID 取单篇、`legacy-scan` 反向扫描代码库里的过时写法。内容覆盖 250 个现代 Web 特性，分六大领域：用户体验（View Transitions、滚动驱动动画）、CSS 布局（容器查询、subgrid、oklch）、性能（预加载、INP 诊断、`scheduler.yield`）、表单与 UI（Popover、dialog、锚点定位）、无障碍，以及浏览器内置 AI。

这个仓库本身负责「作者、校准、评测」：包含内容生产代码、Eval Dashboard 和 GOVERNANCE / CONTRIBUTING 治理文件。它是今年 1 月底才建仓的项目，今天站上 5,534 星，单日 +1,225 继续领跑——昨天的 +1,875 刚把它送上榜首，今天热度没有掉。

💡 可借鉴的优点

- **产品思维**：没有再做一本文档站，而是把「浏览器厂商的权威知识」做成 Agent 可直接消费的技能，卡位在 LLM 的知识盲区上。
- **架构设计**：技能 + CLI 双入口，能整体安装也能按需检索；`legacy-scan` 还能反向审计存量代码，形成「正向指导 + 反向体检」的闭环。
- **工程化**：用评测驱动内容裁剪——只保留模型不掌握的专家级内容，把 token 效率当成可量化的指标，并公开 Eval Dashboard。
- **社区运营**：Chrome、Edge、Firefox、MDN 四个团队联署，跨厂商背书本身就是极强的信任资产。

🌟 特别亮眼的地方

浏览器厂商开始**亲自为 Agent 编写「知识供给侧」内容**，这是一个信号：竞争已经从「模型能不能写」延伸到「喂给模型的知识够不够新、够不够准」。当四大浏览器团队愿意共同维护一份 Agent 技能，现代 Web 的事实标准就有了一个面向 AI 的官方入口。

📖 项目是干什么的

这是阿里集团内部「官方 AI 代码审查助手」的开源版：两年间服务了数万名开发者、识别出数百万个代码缺陷，经过大规模验证后才孵化成开源项目。安装后得到 `ocr` 命令，配置一个模型端点即可使用。

它的工作方式是读 Git diff，把变更文件交给一个具备工具调用能力的 Agent——Agent 可以读完整文件、检索代码库、查看其它变更文件以获取上下文，最终输出**行级精度**的评审意见，而不是浮于 diff 表面的泛泛点评。除 diff 评审外，`ocr scan` 可以对整个文件做审计，适合接手陌生代码库。

真正的差异点在架构：**确定性的工程逻辑 × Agent**。不该出错的部分交给代码——精确的文件筛选、智能文件打包（例如 `message_en.properties` 与 `message_zh.properties` 合并成一个评审单元，各自跑隔离子 Agent，天然支持并发）、模板引擎驱动的细粒度规则匹配、独立的评论定位与反思模块；该动态判断的部分交给模型——场景化 prompt 与从生产调用链里蒸馏出的专用工具集。

数据也拿得出手：AACR-Bench 基于 50 个热门开源仓库、200 个真实 PR、10 种语言，由 80+ 资深工程师交叉标注出 1,505 条 ground truth。官方口径是：同一底座模型下，Precision 与 F1 明显高于通用 Agent，token 消耗约为其 1/9，代价是 Recall 更低——这是主动取舍，宁可少报也不制造噪声。

💡 可借鉴的优点

- **产品思维**：不跟通用 Agent 抢「全能」，而是承认纯语言驱动缺乏硬约束，用工程把底线兜住。
- **架构设计**：文件打包 + 隔离子 Agent 的「分而治之」，是超大 changeset 下保持稳定的关键；定位与反思拆成独立模块，也是可复用的做法。
- **工程化**：自建 benchmark、把数据集放到 HuggingFace，把「审查质量」拆成 F1 / Precision / Recall / 耗时 / token 五个可测指标，并拿到 OpenSSF Gold。
- **社区运营**：多语言 README（中/日/韩/俄）、官网、npm 分发、兼容 Claude Code、Codex、Cursor、Kimi Code，接入面铺得很宽。

🌟 特别亮眼的地方

它把「AI 评审 AI 写的代码」从玄学拉回可复算的工程问题：**精度优先、召回让位**，是面向真实 CI 流水线的取舍，而不是刷榜。当 Agent 写的代码越来越多，「谁来判断它对不对」会变成比生成能力更刚性的需求。

📖 项目是干什么的

Chrome DevTools 团队出品的 MCP Server 与 CLI，让编码 Agent（Antigravity、Claude、Cursor、Copilot 等）能够**控制并检查一个真实的 Chrome 浏览器**。这是「让 Agent 能动手」到「让 Agent 能看见问题」的关键一跳。

三个核心能力：用 DevTools 录制 trace 并抽取可执行的性能洞察；分析网络请求、截图、读取 console 消息（带 source map 后的堆栈）；用 puppeteer 执行动作并自动等待结果，保证自动化可靠。性能工具还可以把 trace URL 发给 Google CrUX 换取真实用户体验数据，让实验室数据与线上场数据并排看——不想要的话 `--no-performance-crux` 一键关闭。

边界写得很清楚：只官方支持 Chrome 与 Chrome for Testing，其它 Chromium 内核浏览器不保证；默认收集使用统计（可 `--no-usage-statistics` 关闭，CI 环境自动关闭）；更新检查同样可关。Apache-2.0，2025 年 9 月建仓，一年时间做到 5.6 万星、4,646 个 fork。

💡 可借鉴的优点

- **产品思维**：Agent 会写前端但不会「看」前端，把调试能力通过 MCP 直接接进模型，痛点被命中得很准。
- **架构设计**：MCP 与 CLI 双形态，复用 puppeteer 和 devtools-frontend，官方团队反而最懂得不重复造轮子。
- **工程化**：明确的兼容边界、遥测默认开启但可关闭、CI 下自动关闭——把「隐私与可运维」当成设计约束而非事后补丁。
- **社区运营**：工具参考、FAQ、设计原则、故障排查齐全，官方维护降低了信任成本。

🌟 特别亮眼的地方

浏览器自动化的竞争点正在从「能不能点」转向「点完能不能解释为什么慢」。当性能 trace、console 与网络时序成为 Agent 的一等输入，前端 Agent 才算真正具备「可观测性」——这是 MCP 生态里少数由被观测方自己提供的服务。

📖 项目是干什么的

Sure 是个人财务应用的社区续作。它原本叫 Maybe Finance：团队在 2021—2022 年砸了将近 100 万美元做一整套个人财务与财富管理功能，甚至提供真人 CFP/CFA 顾问服务，但 B2C 商业模式没跑通，2023 年中停止开发、把代码开源，短暂上线过托管版也未能持续。现在是社区 fork 在维护。

功能上它是一套完整的自托管方案：Docker 一条命令起服务；可以从浏览器、macOS 桌面端、移动端、API 客户端以及 LLM Agent 访问；技术栈是 Ruby on Rails + PostgreSQL + Redis，本地开发用 `bin/setup` 与 `bin/dev`，还能一键灌入演示数据（`rake demo_data:default`）。

值得一提的是它把「性能问题」公开化了：维护团队把 demo 站上的慢请求连同堆栈放到 Skylight 公共看板上，欢迎任何人来提优化 PR。AGPL-3.0，2025 年 7 月建仓，15,095 星、1,146 个 fork。

💡 可借鉴的优点

- **产品思维**：一个商业失败但工程有价值的项目，通过社区 fork 而不是「fork 出走」的方式续命，路径值得研究。
- **架构设计**：Rails 单体承载多客户端 + API + Agent 接入，一套领域模型服务多种终端，复杂度可控。
- **工程化**：公开性能看板让「优化」有靶子和数据，比空喊「欢迎 PR」有效得多。
- **社区运营**：把商标与归属写进 README（禁止 fork 使用 Maybe 商标），提前规避法律摩擦，这是成熟做法。

🌟 特别亮眼的地方

GitHub 上有大量「作者跑路」的项目直接烂尾，Sure 给出了另一种可能：**代码资产可以脱离公司存续**，只要有人愿意接、且授权（AGPL）允许接。它在 Agent 时代还有额外意义——一个能被 LLM Agent 调用的财务 API，本身就是新的产品边界。

📖 项目是干什么的

这是一个起点非常「个人」的项目：作者想用 AI 改进自己的交易流程，于是把「市场复盘—风险管理—交易计划—日记—复盘改进」整套流程拆成了 Claude Skills。它的目标写得很克制——**不是把买卖决策外包给 AI**，而是把决策过程结构化；也不是信号服务，不承诺盈利。

组织方式很像一个正经工程：`skills/` 放单个技能（每个含 SKILL.md、参考资料、辅助脚本），`skills-index.yaml` 是**唯一权威索引**（README 与 CLAUDE.md 冲突时以它为准），`workflows/` 用 YAML 定义五条操作流：15 分钟日检（market-regime-daily）、周度长期组合复盘、只在风险允许时找波段机会、每笔平仓后的记忆回路、月度绩效复审。`skillsets/` 再按目标打包成六种安装组合。

难能可贵的是它照顾了「没有付费数据源的人」：五技能起步路径用公开 CSV、图表截图和本地 YAML 日记即可跑通，FMP / FINVIZ / Alpaca 都是可选。MIT 许可，2025 年 10 月建仓，4,523 星、894 个 fork，还提供日文文档与完整的免责声明。

💡 可借鉴的优点

- **产品思维**：把「决策过程」当成产品，而不是把「预测」当成产品——这是高风险领域里最清醒的定位。
- **架构设计**：skills / workflows / skillsets 三层结构，技能可单用、可编排、可打包，扩展性很自然。
- **工程化**：schema 校验器（`--strict-workflows`）、发布包 SHA256SUMS 校验、明确的版本兼容与迁移策略，规格接近正式软件。
- **社区运营**：免责声明写得比功能还认真，example run 直接展示产物长什么样，降低新人的理解成本。

🌟 特别亮眼的地方

这是 Agent 技能第一次大规模进入「高风险决策」领域，但它的答案不是「让 AI 替你决定」，而是「让你按流程决定」。**技能的价值可以是约束人的随意性**，这条思路在投资、医疗、合规等场景都能复用。

📖 项目是干什么的

Univer 是一个 Office SDK，目标是把「电子表格、文档、演示、关系表、画布、PDF」的编辑、计算、协作与文件处理能力，嵌进你自己的产品里——给人用，也给 Agent 用，并且用的是你的数据和你的权限。

它拆成三块：**Web SDK** 是地基（内容模型与快照格式、编辑与渲染、公式计算、Facade API、插件与依赖管理、命令系统），既可以嵌成编辑器，也可以 headless 复用同一套模型与计算；**Server SDK** 负责实时协作、编辑历史与 Office 文件导入导出；**AI SDK** 把 Office 能力接给现有 Agent 与工作流，提供内容工具、执行与审阅集成。

本仓库开源的是 Web SDK 的核心架构与引擎实现（Apache-2.0），商业插件、Server SDK 与商业 AI 扩展另行授权。开源部分的能力已经相当完整：单元格样式、合并单元格、单元格内富文本、冻结窗格、浮动图片、撤销重做；公式、定义名称、筛选排序、数据校验、条件格式、超链接、评论、查找替换；Docs 侧的富文本、段落格式、列表、链接与绘图集成。2022 年 9 月建仓，今天 24,295 星、2,104 个 fork。

💡 可借鉴的优点

- **产品思维**：把 Excel / Word 当成 SDK 而不是产品来卖，卖给的是「想在自己产品里塞一个表格」的团队。
- **架构设计**：插件与依赖管理 + 命令系统 + 可 headless 的计算引擎，让同一份逻辑既能渲染也能被 Agent 调用，这是很关键的复用设计。
- **工程化**：Codecov 覆盖率、CodeFactor、构建流水线、多包发布，开源部分的工程规格不低。
- **社区运营**：多语言 README、Showcase、Open Collective 赞助、Discord 社区，商业与开源边界讲得清楚。

🌟 特别亮眼的地方

「让 Agent 直接编辑你的表格和文档」不是接个 LLM 就完事，底层必须支持**可撤销、可协作、可复算**——公式算错一次就可能污染整张表。Univer 押注的正是这层别人不愿意啃的脏活，一旦成立，它就是 Agent 办公场景的地基。

💡 可借鉴的优点

- **产品思维**：模型厂商把「自家模型的默认入口」做成开源 Agent，用生态换默认选择权。

「模型与 harness 同源演进」是 Qwen 的差异化打法。今天的编码 Agent 竞争，越来越不是比谁的权重更强，而是比**谁更懂自己的模型该被怎么驱动**——这一步，模型厂商比第三方套壳更有优势。

📖 项目是干什么的

Plannotator 是一个跑在本地的**浏览器审阅面板**，专治「Agent 干得太快、人跟不上」。当 Agent 提出一个决策、一份计划、一个 HTML 产物，或者刚干完一段活，界面会自动在浏览器里打开，你可以在上面标注、评论，然后一键把反馈发回给 Agent 让它接着做。

接入面很广：Claude Code、Codex、Copilot CLI、Gemini CLI、OpenCode、Kiro、Droid、Amp、DeepSeek Harness、Pi 都支持，靠插件、hooks 和命令挂上去；个人助理类（Grok Bot、Muse、Hermes、OpenClaw）则通过 Inbox 接入。功能上分三块：标注计划 / 规格 / Markdown / HTML 等交互产物；代码审阅（本地 diff 或远程 PR，兼容 Git、GitButler、Jujutsu、Perforce、GitHub、GitLab）；以及新推出的 Plannotator Inbox——把多个 Agent 的提问、文件、待评审内容汇总到一个本地窗口，点一下就能回答，回复会回到提问的那个会话，不会把会话卡住。

它还留了 MCP 入口（`plannotator inbox mcp`）和终端形态的 Herdr Annotate。今天 10,796 星、+412。

💡 可借鉴的优点

- **产品思维**：Agent 越自主，人越需要一个「低摩擦的介入点」——不是审批弹窗，而是能写批注的画板。
- **架构设计**：本地服务 + 浏览器 UI + 插件/Hook/MCP 三种接入方式，覆盖从 CLI 到个人助理的全谱系。
- **工程化**：多版本控制系统（Git / GitButler / Jujutsu / Perforce）与多代码托管（GitHub / GitLab）适配，说明它按真实工程环境设计。
- **社区运营**：官网、文档、演示视频、HTML 视觉技能配套，把「怎么用」讲得很轻。

🌟 特别亮眼的地方

人机协作的瓶颈已经从「生成」转移到「审阅」。Plannotator 的价值在于把**批注变成 Agent 可执行的结构化输入**——不是人改代码，而是人指出哪里不对，Agent 去改。这一层如果标准化，会成为 Agent 工作流的标配环节。

## 📊 今日趋势洞察

**核心方向：审阅层（Review Layer）正在成为 Agent 栈的新一层。**

把今天的 10 个项目按工作流位置排一下就很清楚：modern-web-guidance 管「写之前的规范」，open-code-review 管「提交时的审查」，chrome-devtools-mcp 管「运行时的观测」，plannotator 管「决策时的批注」。四个项目、四个关口，都在解决同一个问题——**Agent 做事越来越快，人类理解与纠错的速度跟不上**。这不是巧合，而是当生成能力过剩之后，必然溢出的需求。

**升温领域：技能工程化、MCP 作为能力接口、本地与自托管优先。**

claude-trading-skills 用 `skills-index.yaml` + workflow manifest + schema 校验器把技能做成了可发布的软件件；univer 把 Office 拆成 SDK 供 Agent 调用；qwen-code 用自家 harness 驱动自家模型。另一边，sure 与 uptime-kuma 的回升、Veyra 的本地 GPU 管线，都在指向同一个取向：**能自己掌控的数据与算力，优先级在上升**。MCP 也从「连接工具」进化成「官方能力出口」——Chrome DevTools 直接提供 MCP Server，就是最强的信号。

**对开发者的三点启发。**

第一，把确定性的部分写成代码，把判断的部分留给模型——阿里这套「确定性工程 × Agent」的分工，比任何 prompt 技巧都更能稳住质量。第二，给 Agent 写「知识」必须带评测：现代 Web 指南靠评测裁剪内容，代码审查靠 benchmark 校准精度，没有度量的技能只是文案。第三，一定要给人类留一个低成本介入点：无论是 Plannotator 的批注画板，还是 open-code-review 的行级评论，**可被反驳的自动化，才敢放进生产**。
