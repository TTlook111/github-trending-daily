📖 项目是干什么的

Claude-BugHunter 是一套只面向**授权范围内**外部安全测试的 Claude Code 技能包，今天连续第四天排在第一。规模没变：85 个技能、16 个斜杠命令，知识底座是从 681 份公开披露报告里整理出的模式库（覆盖 24 类核心漏洞，其中 433 条逐条标注了出处），按“方法论、Web 应用、企业平台、报告与验证”四层组织。仓库今年 5 月建仓，MIT 协议，2,583 个 fork。

今天早上 8 点 43 分到 10 点 38 分，作者不到两小时合入了 8 笔提交，全部在修“守门工具自己的问题”，主线仍是昨天那条——范围校验不能“失败即放行”。第一笔（由外部研究者报告）关掉了 5 个同类问题，提交说明里特意写了一句：没有逐个拼写去打补丁，而是归因成两种模式——一是规则被规范化了，但目标主机的 IP 字面量没有，于是同一个范围外地址换一种写法就能进来；二是有几处代码在拼接 URL 时直接采用了来自不可信输入的主机部分，没有经过范围检查。修法是把 IP 字面量按与规则相同的方式规范化，并在每一个“基址 + 路径”的拼接处加一道检查。半小时后的第二批是作者根据社区报告在内部重做的：范围规则里一条带行内注释的 CIDR 拒绝规则没有被识别成网段，等于这条拒绝规则从来没生效过；脚手架脚本 `hunt` 没有校验目标名，传入带路径分隔符的名字可以在目录之外建文件夹。提交里逐条署名了报告者，没有直接合并对方的 PR。

第三类是“数字写错了”。作者做了一次端到端自查，发现仓库里只有 7 个文件受“文档里的技能数、命令数是否正确”的检查覆盖，另外 7 个写着 85 / 58 / 16 的地方没有任何校验——而这正是过去反复出现“数字过期”的原因。于是检查范围从 7 个文件扩到 21 个、断言从 21 条扩到 42 条，并立刻抓到一个现成的错：首页横幅上的“命令数”写着 15，其余所有地方都是 16。其余几笔是工程面的：给 `cbh` 命令行加了基于 OIDC 的 PyPI 受信发布流程（不保存任何令牌，标签与项目版本号不一致时构建直接失败）；README 把安装方式改成以已发布的 PyPI 包为先；把两份技能文档里从上游原样继承来的“去第三方仓库 `curl` 一个未固定版本的文件”的安装段落，换成了本包自己的安装路径；还有一笔把一份验证记录里贴出来的本机账户名抹掉。

💡 可借鉴的优点

- **产品思维**：对“报告了漏洞的人”给出明确的处理方式——不改写对方发现的问题，逐条署名，并在提交里说明为什么在内部重做而不是直接合并。
- **架构设计**：同一类问题归因成模式而不是拼写：把“规则怎么规范化”收敛成一个函数，目标主机和范围规则走同一条路径，避免每来一种写法就补一次。
- **工程化**：把“首页数字过期”从靠人记变成 CI 断言，而且扩完当天就抓到一个现成的错；发布链用不存令牌的受信发布，并让版本不一致成为硬失败。
- **社区运营**：一个上午回应了四位报告者（@chaitanya0305、@basanta-codexa、@speto2、@patsevanton）；对文档里的小疏漏（泄漏本机账户名、继承自上游的安装说明）同样当作正式提交处理，而不是顺手改掉不留记录。

🌟 特别亮眼的地方

今天有两笔提交放在一起看特别有意思。一笔修的是“断言全部通过、步骤却报红”——Windows 下 `hunt` 正确拒绝了非法目标名，但拒绝时留下的退出码让整个 PowerShell 步骤被判失败；另一笔修的是“改了测试脚本或工作流文件，冒烟测试却被静默跳过”——因为触发路径里没列这两个文件。前者是**假警报**，后者是**假安静**，正好是昨天“失败要响亮”那句话的正反两面。守门工具做到第四天还在修自己的门，这不是坏事：一个声称能替你拦住风险的工具，最可信的证据就是它对自己的怀疑从没停过。

📖 项目是干什么的

Firecrawl 是给 AI Agent 用的“网页数据基础设施”，同一个能力做成三种形态。**Firecrawl Local** 是一个 Rust 写的单文件，`cargo install firecrawl-local` 装完就能抓取、爬站、列 URL，不需要数据库、队列和容器，`init` 会自动发现自己机器上的 Claude Code、Cursor、Codex 等并注册成 MCP 服务。**Firecrawl Cloud** 在此之上加搜索、结构化输出以及 Alexandria——550 多家数据提供方通过一个 API / MCP / CLI 接入。**自托管**是带队列、worker 和数据库的完整 API 服务。仓库 2024 年 4 月建仓，AGPL-3.0 协议，11,085 个 fork，今天 +1,046，从昨天的第 3 回到第 2。

过去 24 小时它只合入了 1 笔提交：今天 0 点 21 分，由社区贡献者提交，标题是“从 markdown 和 html 里剔除 NUL 字符”（#6104）。NUL 是一个几乎不会被人看见的字符，但对下游很致命——很多数据库、日志系统和文本处理工具把它当作字符串的结尾，一段网页正文里只要混进一个，后面的内容就可能被悄悄截断。抓取工具面对的是整个互联网的页面，遇到什么都不奇怪；这类问题往往不是“功能不对”，而是“输出让别人的系统出错”。相比昨天那八笔围绕“丢失的爬取状态要响亮地处理”的提交，今天这一笔小得多，但它属于同一类工作：把不干净的东西拦在边界上，而不是交给调用方去猜。

没有新的 Release。昨天上午连发的七个 API 镜像版本（v2.11.865 到 v2.11.871）之后，今天没有再发。Local 这一层的细节保持不变：`serve` 在本机 3002 端口提供与云端 v2 API 兼容的接口，本地路由不需要 API Key；单页抓取在本地打不开时默认转给云端并在结果里标注来源。

💡 可借鉴的优点

- **产品思维**：三档形态分别对应“想马上试”“不想运维”“数据不能出门”，Local 不是阉割版。
- **架构设计**：输出格式是契约的一部分——清理 NUL 这种事由生产方在边界完成，几十个 SDK 和所有下游调用方都不必各写一遍。
- **工程化**：镜像跟随主干滚动发版；昨天的爬取状态存储、鉴权过期、临时文件归属三件事都带了测试用例。
- **社区运营**：今天唯一的提交来自外部贡献者，一个二十一万星的项目仍然接收一行级别的小修。

🌟 特别亮眼的地方

一个二十一万星的项目，今天做的是剔除一个看不见的字符。这件事的价值在于它回答了一个常见的问题：成熟项目的日常是什么？不是新能力，而是**让输出更“可被信任”**。对一个被成千上万 Agent 当作数据入口的工具来说，别人拿到的每一段文本都应该是干净的——这比多支持一个抓取选项重要得多。

📖 项目是干什么的

Diagram Design 是一个“让 Agent 画出你愿意发布的图”的技能：用大白话描述需求，Agent 自己选类型、说出计划，然后写出一个自包含的 HTML 文件（内联 SVG，无外部依赖），双击就能打开，可导出 PNG 或 SVG。52 种图表类型，每种有极简浅色、极简深色、完整编辑风三个变体。仓库今年 4 月建仓，MIT 协议，4,980 个 fork，今天 +955，从昨天的第 2 退到第 3。

昨天它一整天零提交，今天有了两笔来自社区的修复，都落在 Mermaid 导入上。第一笔（#282，凌晨 1 点 33 分）解决的是资源问题：导入一份含多段 Mermaid 的文档时，用户只选了其中一段，原实现却会把没选中的块也拿去解析——解析是整个流程里最贵的一步，而选中的图之外只要有一段写坏的代码，就可能把解析器的资源耗掉。修法是没选中的块只列出来、不解析，并在导入指引里写明“只解析选中的块”。第二笔（#550，凌晨 3 点 48 分）是兼容性：Mermaid 允许 `flowchart` 或 `graph` 标题后面不带方向，原实现不认这种写法，现在默认按从上到下导入，与 Mermaid 本身的行为一致，并在校验脚本里补了这类标题形式的用例。两笔提交之后，自动化流程各提了一次插件版本号（2.6.180、2.6.181）。

它的核心资产没变：一份写得非常具体的“品味说明书”——只用一个强调色，1px 细线，不用阴影，圆角最大 10px，所有坐标、宽度、间距都能被 4 整除，目标密度 4/10。工程上按需加载：Agent 启动时只看到技能的名字和描述，请求命中后才加载 SKILL.md，再按需拉一个类型参考。

💡 可借鉴的优点

- **产品思维**：把“从 Mermaid / draw.io / PlantUML / Excalidraw 迁过来”当成正式入口来做，兼容性问题按源工具的真实行为修，而不是要求用户先改写。
- **架构设计**：“选什么就解析什么”——解析范围由用户的选择界定，没选中的内容不进入昂贵且容易出错的路径。
- **工程化**：每个修复都往校验脚本里加用例；版本号由合并后的自动流程统一提升，一天两次。
- **社区运营**：两笔修复都来自外部贡献者，当天合并、当天出版本；仓库还明确声明官方构建只来自本仓库。

🌟 特别亮眼的地方

#282 是一笔很小但思路很对的修复。很多系统默认“把输入整体处理一遍再说”，于是用户没选、不需要的内容也能让程序变慢甚至卡死。把处理的边界对齐到“用户实际要的那一块”，既是性能问题，也是安全问题——今天的另一边，Claude-BugHunter 花了一上午在给“不可信输入不该到达的地方”加检查，diagram-design 用一笔提交说的是同一件事：**不该处理的，就别让它进来。**

📖 项目是干什么的

Ghost Downloader 是一个跨平台下载器，口号是“The only downloader you need / 下载器的集大成者”。HTTP、磁力 / BT、FTP、M3U8、MPEG-DASH、eD2k 六类协议收在一个应用里；YouTube 与 Bilibili 支持分 P、任意清晰度和字幕；配上浏览器扩展可以嗅探页面媒体。Windows、macOS、Linux、Android 四端原生。仓库 2023 年 8 月建仓，GPL-3.0 协议，1,200 个 fork，今天 +889，从昨天的第 5 升到第 4。

昨晚是它这几天最忙的一晚：从晚上 8 点半到 10 点，作者合入了 8 笔提交，并于 9 点 33 分发布了 v4.6.1。版本说明里是六条修复，其中三条都是“用户能直接感知”的问题。最要紧的一条是打包版里缺了一个 Python 标准库模块（`optparse`），导致 YouTube 等视频下载直接报错——issue 里接连有三个人报告（#1208、#1216、#1218）。第二条是系统关机或重启时任务记录和 BT 做种分享率没保存就退出了，修法是在关机时延缓系统退出，先把记录写盘（#1200）。第三条是取消或暂停下载后电脑无法进入睡眠，Linux 下下载时还会阻止合盖与手动睡眠（#1141）。其余三条是桌面端偶发崩溃、macOS 上被浏览器扩展唤醒后点 Dock 图标不弹主窗口（#1186），以及昨天社区贡献者修的“功能包更新提示未翻译”。此外还升级了界面组件库，并同步了巴西葡萄牙语、俄语、越南语三份译文。

版本说明的开头仍然挂着那句话：由于本人学业原因，更新节奏有所放缓。但这一版的内容说明，“放缓”指的是节奏，不是质量——六条修复每一条都对应着 issue 编号或可复现的场景。

💡 可借鉴的优点

- **产品思维**：修复清单写给用户看，每一条都是能感知的场景——“电脑睡不着”“关机后记录没了”，而不是“修复了若干缺陷”。
- **架构设计**：把“变得快的部分”（站点规则、协议细节）做成功能包，与“变得慢的部分”（界面、调度）解耦；底子是 Python + PySide6，网络层跑在 asyncio 上。
- **工程化**：译文在 Crowdin 上管理并由机器人自动同步；版本文件随发版自动更新；每条修复都能追溯到 issue。
- **社区运营**：QQ 群与 Discord 双通道，Arch Linux 有社区维护的 AUR 包；外部贡献者的修复进入正式版本说明并署名。

🌟 特别亮眼的地方

v4.6.1 里最值得记的是那个缺失的模块：它只在**打包后**的环境里出问题，开发者自己从源码运行时永远不会遇到。这是桌面软件最典型的一类盲区——开发环境和用户拿到的安装包不是一回事。作者在同一晚就把三个人报的同一个问题关掉，第二天名次上升一位，日增只比昨天少 62，是榜上最稳的几个之一。对一个声明“更新放缓”的学生项目来说，这比任何路线图都更有说服力。

- **架构设计**：数据与逻辑分离——拒审模式、法规截止日期各自是数据文件，检测配方由数据生成，所以数据更新可以单独发版。
- **工程化**：规则改动做双向测试；连“注释里的字符串”这种误报也当作正式问题修；引用来源有专门的校验脚本。
- **社区运营**：外部贡献者的修复带编号进入主干；对暂时无法确认钩子格式的工具，给出手动步骤而不是猜一个格式写进去。

🌟 特别亮眼的地方

今天它掉到第十，是四天里最低的名次，但三笔提交说明它并没有慢下来。其中最值得借鉴的是 #2426：**守门工具最容易出错的地方，往往不是检查逻辑，而是它所依据的那条规则本身有没有抄对。** 一个法规的生效日期、适用范围，如果来自某篇博客而不是法案原文，那么检查写得再严谨也是建在沙子上。数据来源要追到一手文件——这条原则适用于任何以“规则”为产品的工具。

**核心方向：原班人马第四天——一起踩刹车，各自补门。**

十个项目连续四期没有换人，今天十个的日增全部低于昨天，合计少了 1,513。但名次依然在大幅洗牌：第 2 名到第 10 名的差距从 315 拉大到 484。**有新提交的七个**：Claude-BugHunter（9 笔）、last30days（18 笔、两个版本）、Ghost-Downloader-3（10 笔、v4.6.1）、AutoClip（6 笔、v1.6.2）、diagram-design（4 笔）、app-store-compliance（3 笔）、firecrawl（1 笔）；**没有新提交的三个**：superpowers、CLI-Anything、minimind。日增降幅最小的两个是 superpowers（−49）和 Claude-BugHunter（−55），最大的两个是 CLI-Anything（−360）和 app-store-compliance（−296）——前者一行没动，后者一天三笔提交。和昨天一样，**提交多少与涨跌快慢之间看不出关系。**

**升温领域：把自查做成流程、把边界画在解析之前、把说过头的话收回来。**

三个信号。其一，**“自查”开始变成可执行的流程**：Claude-BugHunter 把“文档里的数字对不对”从 7 个文件的检查扩到 21 个、断言从 21 条扩到 42 条，当天就抓到首页横幅上一处现成的错；同一个上午它还修了“断言全过却报红”和“改了测试却被静默跳过”两件事——一个假警报，一个假安静。其二，**处理的边界被前移到“用户实际要的那一块”**：diagram-design 只解析选中的 Mermaid 块，选中的之外的坏内容碰不到解析器；Claude-BugHunter 给每一个“基址 + 路径”的拼接处加检查，不让不可信输入决定请求发往哪里；firecrawl 在输出边界剔除 NUL 字符。三个项目、三种场景，说的是同一件事——不该进来的，就别让它进来。其三，**“说得更保守”成了正式的改动**：AutoClip 把“零水印”改成“无付费墙”，理由是更准确；app-store-compliance 把一条法规的来源改成一手的法案文本；last30days 新增的两个来源都是可选、免 key 的。

**对开发者的三点启发。**

第一，**读榜要看相对，不看绝对。** 全员下调的日子里，名次上升只说明别人退得更快；一个三周没动的仓库能从第 7 回到第 5，一个一天 18 笔提交的项目会从第 6 退到第 7。想判断一个项目的状态，去看它的提交、版本说明和变更日志，比看 star 诚实得多。第二，**把自己当审计对象，并且写成断言。** “首页数字过期”“测试通过却报红”“工作流被静默跳过”这三件事没有一件是新功能，但每一件都会让信任漏一点；它们的共同点是都可以被一条 CI 检查覆盖——前提是有人先把它当成问题。第三，**修文档和修代码一样值得一次正式提交。** 把说过头的宣传语改准确、把规则的来源换成一手的法案文本，这些改动很小，但它们决定的是用户在遇到问题时还愿不愿意相信你。
