📖 项目是干什么的

这是 Modern Web Guidance 的源码仓库，真正的产物是 `GoogleChrome/modern-web-guidance` 那套面向编码 Agent 的技能。要解决的是 LLM 的老毛病：训练数据里堆满旧代码，Agent 总爱用臃肿的 JavaScript 去实现浏览器早就原生支持的能力；就算模型知道某个 API 存在，也缺生产可用的现代写法密度。

机制上有四个 CLI 入口：`install` 交互式安装、`search` 检索指南、`retrieve` 按 ID 取单篇、`legacy-scan` 反向扫描代码库里的过时写法。内容覆盖 250 个现代 Web 特性，分六大领域：用户体验（View Transitions、滚动驱动动画）、CSS 布局（容器查询、subgrid、oklch）、性能（预加载、INP 诊断、`scheduler.yield`）、表单与 UI（Popover、dialog、锚点定位）、无障碍，以及浏览器内置 AI。

今天它已经连续第四天坐在榜首，星数 7,673、单日 +1,219，四天累计净增超过 5,200。这个仓库自己不管「写内容」，管的是作者、校准与评测：内容生产代码、Eval Dashboard、GOVERNANCE / CONTRIBUTING 治理文件都在这里；407 个 open issue 也说明它是个高频迭代的内容工程，而不是发一次就完的文档。

💡 可借鉴的优点

- **产品思维**：不做文档站，把「浏览器厂商的权威知识」做成 Agent 可直接消费的技能，卡位在 LLM 的知识盲区上。
- **架构设计**：技能 + CLI 双入口，能整体安装也能按需检索；`legacy-scan` 反向审计存量代码，形成「正向指导 + 反向体检」的闭环。
- **工程化**：用评测驱动内容裁剪，只保留模型不掌握的专家级内容，把 token 效率当可量化指标并公开 Eval Dashboard。
- **社区运营**：Chrome、Edge、Firefox、MDN 四个团队联署，跨厂商背书是最硬的信任资产。

🌟 特别亮眼的地方

一门「技能」能连续四天霸榜，说明它踩的不只是热点，而是**标准制定权**：当浏览器厂商开始为 AI 编写知识供给侧的内容，现代 Web 的事实标准就有了一个面向 Agent 的官方入口。它的真正护城河不是那 250 条特性，而是「谁来定义什么叫过时」——`legacy-scan` 这个反向审计能力，等于握住了存量代码的判定权。

📖 项目是干什么的

Univer 是一个 Office SDK，目标是把「电子表格、文档、演示、关系表、画布、PDF」的编辑、计算、协作与文件处理能力嵌进你自己的产品——给人用，也给 Agent 用，用的是你的数据和你的权限。

它拆成三块：**Web SDK** 是地基（内容模型与快照格式、插件与依赖管理、命令系统、公式与渲染引擎、Facade API、UI 基础），既能嵌成编辑器，也能 headless 复用同一套模型与计算；**Server SDK** 负责实时协作、编辑历史与 Office 文件导入导出；**AI SDK** 把 Office 能力接给现有 Agent 与工作流。开源的是 Web SDK 的核心架构与引擎（Apache-2.0），商业插件与 Server / AI 扩展单独授权，功能对照表写得很清楚。

今天它从昨天的 +495 直接翻到 +988，是本期增幅提升最大的项目。这个数字背后的逻辑不难猜：Agent 办公的想象力不缺了，真正稀缺的是「扛得住真实编辑操作」的地基。跨特性撤销就是个典型例子——在筛选范围内插入一行，会同时改动本体内容与筛选范围，撤销必须把两者一起还原；每个特性各自提供变更与撤销数据，由命令系统组合执行与历史。快速上手只要 `pnpm add @univerjs/presets @univerjs/preset-sheets-core`，一个预设就拿到完整表格编辑器；在 Node.js 里还能复用同一套插件与模型做快照处理与自动化。

💡 可借鉴的优点

- **产品思维**：把 Excel / Word 当成 SDK 而不是产品来卖，卖给「想在自己产品里塞一个表格」的团队。
- **架构设计**：插件与依赖管理 + 命令系统 + 可 headless 的计算引擎，同一份逻辑既能渲染也能被 Agent 调用。
- **工程化**：开源与商业边界公开（功能对照表 + 授权说明），避免「先用后付费」的信任崩塌。
- **社区运营**：多语言 README、Showcase、Open Collective 赞助、Discord 社区，商业与开源分工讲得明白。

🌟 特别亮眼的地方

增幅翻倍的时间点很微妙：就在「审阅层」连涨三天之后。我的解读是，市场正在从「怎么让 Agent 少犯错」转向「怎么让 Agent 真的产出一份可交付的文件」。**审阅是成本，产出才是收益**——当省下来的功夫开始被要求兑现成文档与表格，Office 这一层就从配角变成了必经之路。

📖 项目是干什么的

Plannotator 是一个跑在本地的浏览器审阅面板：当 Agent 抛出一个决策、一份计划、一个 HTML 产物，或者刚干完一段活，界面自动在浏览器里打开，你在上面标注、评论，再一键把反馈发回去让 Agent 接着做。

接入面铺得很宽：Claude Code、Codex、Copilot CLI、Gemini CLI、OpenCode、Kiro、Droid、Amp、DeepSeek Harness、Pi 都能靠插件、hooks 和命令挂上去；个人助理类（Grok Bot、Muse、Hermes、OpenClaw）通过 Inbox 接入。功能三块：标注计划 / 规格 / Markdown / HTML；代码审阅（本地 diff 或远程 PR，兼容 Git、GitButler、Jujutsu、Perforce、GitHub、GitLab）；以及 Plannotator Inbox。

昨天它靠 Inbox 从第 10 跳到第 2，今天 +866 稳在第 3，说明这不是一次发布带来的脉冲，而是留住了人。Inbox 的关键设计还是那两条：所有 Agent 的提问、文件、待评审内容都进同一个本地窗口；回复回到提问的那个会话，**但不挂起会话**——Agent 不用干等人。再加 MCP 入口（`plannotator inbox mcp`）与终端形态的 Herdr Annotate，从 IDE 到纯终端全覆盖。Apache-2.0，2025 年 12 月底建仓，12,175 星、1,146 个 fork。

💡 可借鉴的优点

- **产品思维**：Agent 越自主，人越需要一个低摩擦的介入点——不是审批弹窗，而是能写批注的画板。
- **架构设计**：本地服务 + 浏览器 UI + 插件 / Hook / MCP 三种接入，覆盖从 CLI 到个人助理的全谱系。
- **工程化**：多版本控制系统与多代码托管适配，按真实工程环境设计，而不是只服务一条理想路径。
- **社区运营**：官网、文档、演示视频，把「怎么用」讲得很轻。

🌟 特别亮眼的地方

连续两天高位，把一件事验证了：**审阅产品的核心不是「能标注」，而是「不打断」**。批注变成 Agent 可执行的结构化输入只是第一层，真正让人愿意天天开着的，是那个「不挂起会话」的异步模型——人不必在线，Agent 不必等待。

📖 项目是干什么的

Chrome DevTools 团队出品的 MCP Server 与 CLI，让编码 Agent（Antigravity、Claude、Cursor、Copilot 等）能够控制并检查一个真实的 Chrome 浏览器，把「让 Agent 能动手」推进到「让 Agent 能看见问题」。

三个核心能力：用 DevTools 录制 trace 并抽取可执行的性能洞察；分析网络请求、截图、读取 console 消息（带 source map 后的堆栈）；用 puppeteer 执行动作并自动等待结果。性能工具还能把 trace URL 发给 Google CrUX 换取真实用户体验数据，让实验室数据与线上真实数据并排看，`--no-performance-crux` 一键关闭。边界也写得很清楚：只官方支持 Chrome 与 Chrome for Testing；默认收集使用统计（可 `--no-usage-statistics` 关，CI 环境自动关）。

今天 57,370 星、+717，4,834 个 fork，增幅连续三天走高（+673 → +718 → +717 基本持平）。这类项目的增长曲线很能说明问题：**它不是在「教 Agent 新本领」，而是在给 Agent 补上人类早就有的感官**。

💡 可借鉴的优点

- **产品思维**：Agent 会写前端但不会「看」前端，把调试能力通过 MCP 直接接进模型，痛点命中极准。
- **架构设计**：MCP 与 CLI 双形态，复用 puppeteer 与 devtools-frontend，官方团队反而最懂得不重复造轮子。
- **工程化**：明确兼容边界、遥测默认开启但可关、CI 下自动关——把隐私与可运维当设计约束而非事后补丁。
- **社区运营**：工具参考、FAQ、设计原则、故障排查齐全，官方维护降低了信任成本。

🌟 特别亮眼的地方

当性能 trace、console 与网络时序成为 Agent 的一等输入，前端 Agent 才算真正具备可观测性。而这件事由**被观测方自己**来做，生态位就稳定了——第三方做同类工具永远追不上版本节奏，官方做则天然带着「事实标准」的位置，这也是它增幅能稳在高位的原因。

📖 项目是干什么的

阿里内部「官方 AI 代码审查助手」的开源版：在内部经过大规模真实调用验证之后才孵化成开源项目。装完得到 `ocr` 命令，配一个模型端点即可用；官方口径是「安全、快速、高效，经得起阿里规模考验」。

工作方式是读 Git diff，把变更文件交给具备工具调用能力的 Agent——Agent 可以读完整文件、检索代码库、查看其它变更文件获取上下文，最终输出**行级精度**的评审意见。除 diff 评审外，`ocr scan` 可对整个文件做审计，适合接手陌生代码库。内置多语言规则集覆盖空指针、线程安全、XSS、SQL 注入，模型侧兼容 OpenAI 与 Anthropic 协议。

差异点在架构：**确定性的工程逻辑 × Agent**。不该出错的交给代码——精确文件筛选、智能文件打包（例如 `message_en.properties` 与 `message_zh.properties` 合并成一个评审单元，各自跑隔离子 Agent，天然支持并发）、模板引擎驱动的规则匹配、独立的评论定位与反思模块；该动态判断的交给模型——场景化 prompt 与从生产调用链里蒸馏的专用工具集。仓库 topics 直接写 `harness` 与 `repository-level-context`，态度很坦诚。

AACR-Bench 是它的底气：50 个热门开源仓库、200 个真实 PR、10 种语言、80+ 资深工程师交叉标注出 1,505 条 ground truth。官方口径是同一底座模型下 Precision 与 F1 明显高于通用 Agent，token 消耗约为其 1/9，代价是 Recall 更低——主动取舍，宁可少报也不制造噪声。今天 52,588 星、+691，连续两天稳定在 690 上下。

💡 可借鉴的优点

- **产品思维**：不跟通用 Agent 抢「全能」，承认纯语言驱动缺乏硬约束，用工程把底线兜住。
- **架构设计**：文件打包 + 隔离子 Agent 的「分而治之」，是超大 changeset 下保持稳定的关键。
- **工程化**：自建 benchmark、数据集上 HuggingFace，把审查质量拆成 F1 / Precision / Recall / 耗时 / token 五个可测指标。
- **社区运营**：多语言 README、npm 分发、兼容 Claude Code / Codex / Cursor / Kimi Code，接入面铺得很宽。

🌟 特别亮眼的地方

它把「AI 评审 AI 写的代码」从玄学拉回可复算的工程问题：精度优先、召回让位，这是面向真实 CI 流水线的取舍，不是刷榜。连续三天在榜也说明企业的刚需已经稳定——当 Agent 写的代码越来越多，「谁来判断它对不对」比「谁写得快」更值钱。

📖 项目是干什么的

LoopForge 是腾讯开源的自托管工作台，目标是让团队**用编码 Agent 交付软件**，而不是用编码 Agent 做演示。你在聊天里描述需求，主 Bot（Main Bot）就会开一个 Docker 沙箱、拉取你的仓库、把活派给项目角色，最后开出 PR。

它有两种工作方式：一是「和主 Bot 聊」，适合探索、快速修 bug、边聊边改；二是「跑 SOP」，把一套被验证过的工作方式固化成标准流程（agents + scripts + 人工闸门的组合），下一次需求照同样的路径交付。SOP 引擎按顺序执行四种节点：Agent 节点、Script 节点、Human-gate 节点、子 SOP 节点，各自在自己的沙箱里跑；人在闸门处审批，也可以把活打回指定步骤、重试或从任意节点重跑。

干活的是现成的编码 CLI——CodeBuddy、Codex、Claude Code、OpenCode、Cursor CLI、Antigravity、Kimi Code、Pi、DeepSeek Harness、ZCode。LoopForge 自己补上的是它们缺的那一圈：角色、沙箱、检查点、历史，以及「需求—变更」的追踪（聊天路径和 SOP 路径的改动都会挂回同一条需求，计入交付与成本报表）。Go 写的，MIT 许可，2026 年 7 月建仓，今天 2,109 星、+423。

💡 可借鉴的优点

- **产品思维**：承认「Agent 一次能跑完」和「Agent 每次都跑得一样」是两件事，产品化的是后者。
- **架构设计**：Agent / Script / Human-gate / 子 SOP 四类节点 + 独立沙箱，把流程编排和权限隔离做成了同一套东西。
- **工程化**：检查点、可回退到任意节点、按需求归集成本，这些是「敢放进真实交付」的必备项；兼容十家 CLI 而不是绑定一家。
- **社区运营**：双语 README、80 秒产品演示、FAQ 与文档分区，把「这东西到底怎么用」讲在第一位。

🌟 特别亮眼的地方

它把**「人工闸门」当成流程里的一等节点**，而不是一个事后审批按钮。这个设计很关键：当 Agent 可以在沙箱里连续改代码、跑测试、提 PR，人真正需要的不是「随时盯着」，而是在少数关键节点上有一次决定权。LoopForge 的 SOP 就是把这少数节点固定下来的容器——**流程是给人踩刹车的，不是给 Agent 加速的**。

| 属性 | 信息 |

📖 项目是干什么的

AG-UI 是一个开放的、轻量的事件式协议，用来标准化「AI Agent 如何连接到面向用户的应用」。它要解决的是每个团队都在重复踩的坑：Agent 后端跑在自己的框架里，前端跑在自己的技术栈里，两边每次对接都要现造一套事件约定。

机制极简：Agent 执行过程中，后端发出的事件只要能对上 AG-UI 定义的约 16 种标准事件类型之一即可；后端接收的输入也只需要符合少数几种约定。中间加了一层弹性 middleware，对事件格式做宽松匹配，所以任何传输方式（SSE、WebSocket、webhooks 等）都能用，不强制某一种。官方还提供了参考实现的 HTTP 层与默认 connector，`npx create-ag-ui-app` 直接起一个可跑的应用，另有 Dojo 在线演练场。

它定位不是替代 MCP 或 A2A，而是补上**协议栈里「最后一公里」**——工具怎么被调用有人管了（MCP），Agent 之间怎么对话有人管了（A2A），那 Agent 怎么把状态与过程呈现给人、人怎么把实时上下文喂回去，就归 AG-UI。MIT 许可，2025 年 5 月建仓，今天 18,303 星、+355。

💡 可借鉴的优点

- **产品思维**：不定义「Agent 该怎么做」，只定义「Agent 该怎么被看见」，把自己的边界收得很小，反而更容易被广泛采用。
- **架构设计**：事件类型少（约 16 种）、格式校验宽松、传输无关，这三点加起来就是低接入成本。
- **工程化**：参考实现 + 默认 connector + 脚手架 + Dojo，一套完整的「从能跑到能查」的路径。
- **社区运营**：Discord、文档站、贡献指南，还专门开了「接入新框架」的预约通道，主动扩生态。

🌟 特别亮眼的地方

Agent 的产品体验正在从「一句话进、一段文字出」变成「多步执行、过程可见、随时可干预」。要做到这一点，前端必须能收到细粒度的事件流——AG-UI 押的就是这个必然性。它的价值不在规范本身有多巧妙，而在于**它让「Agent 产品」第一次有了可复用的界面层契约**。

### #10 NVIDIA/SkillEvaluator ⭐

| 属性 | 信息 |
| --- | --- |

📖 项目是干什么的

SkillEvaluator 是 NVIDIA 做的技能评测框架，回答一个所有人都在问但很少有人量化的问题：**装上这条技能之后，Agent 真的变强了吗？** 它分两步走——先做质量检查，再带上模型做「有技能 / 无技能」的对比跑，看技能对任务结果的实际影响。

能力清单很工程化：分层（tier）检查，`skillevaluator validate ./my-skill --tiers 1` 只跑不花 API key 的静态检查；语义重叠检测，用来发现两条技能在指令上的重复与冲突；合成评测数据集生成，帮你从技能内容自动造测试样本；以及 live agent 评测，直接测技能对 Agent 行为的改变量。它属于 NVIDIA 的 Verified Skills 流水线，有对应的 arXiv 论文（2608.20614）和官方文档站。

接入方式三条：直接命令行跑、通过 CI 挂到每次 PR 上（GitHub 上 `skillevaluator ci init` 会自动开一个配置 PR）、或者把评测本身做成一条技能装进 Claude Code / Codex（`npx skills add NVIDIA/SkillEvaluator`，然后就可以直接问「我这条技能行不行」）。PyPI 分发，Python 3.12–3.14，Apache-2.0，2026 年 6 月建仓。今天 2,159 星、+122，是本期第二个补齐位。

💡 可借鉴的优点

- **产品思维**：把「技能质量」做成可外包给别人 CI 的检查项，而不是靠人肉 review 或口碑。
- **架构设计**：静态检查与带模型的实跑分层，让零成本环节先挡掉大部分问题，贵的那层只在必要时跑。
- **工程化**：直接进 CI、出配置 PR、按 PR 增量检查变更的技能——完全按「技能也算代码」的思路设计。
- **社区运营**：论文、文档站、博客、直播答疑全套，用学术与工程双通道建立权威。

🌟 特别亮眼的地方

它把技能从「写得像不像样」推进到「**有没有用、有没有重复、有没有害**」这三个可测维度。语义重叠检测这一项尤其关键——当每个人的 Agent 目录里都装了二三十条技能，指令之间的冲突会变成一种静默的性能损失，而这种损失只有量化才看得见。技能供给扩大之后，质检一定会成为下一个基础设施。

## 📊 今日趋势洞察

**核心方向：技能从「扩产」进入「质检」，编排补上人的位置。**

今天这份榜单最好看的地方，是几组项目刚好凑成了一条产业链：stitch-skills 在生产技能（厂商把产品翻译成 Agent 能力），claude-trading-skills 在做垂直领域的深度技能，modern-web-guidance 在做知识型技能并自带评测面板，SkillEvaluator 则专门给别人的技能打分、查重、做 A/B。**供给、垂直、评测三件事同一天出现在榜上，意味着「技能」这个品类已经走完了从提示词技巧到工程件的过渡**，接下来拼的是质量与治理。

**升温领域：编排层、界面协议，以及「可交付」。**

LoopForge（+423）和 ag-ui（+355）分别回答了同一个问题的两半：多个 Agent 一起干活时，谁来决定顺序与放行（编排 + 人工闸门），以及过程怎么被界面与人看见（事件协议）。而 univer 从 +495 翻到 +988，是这个问题的第三半——**活干完了得有东西交出去**。审阅层（plannotator、chrome-devtools-mcp、open-code-review）继续稳在 700～870 的区间，说明它已经从「新鲜事物」变成了「日常工具」：增速不再暴涨，但也不掉。

**对开发者的三点启发。**

第一，**给技能建评测，比给技能写文档更值钱**：文档决定人愿不愿意用，评测决定 Agent 用了会不会更好；SkillEvaluator 把这件事变成了一个 CLI 加一条 CI 配置。第二，**流程的价值在于收窄人的决策点**：LoopForge 的 human-gate 不是「多一道审批」，而是把「随时盯着」换成「关键处拍一次板」。第三，**接口要小、接入要松**：AG-UI 只定义约 16 种事件类型、格式宽松匹配、传输无关，反而比大而全的规范更容易被采用——协议设计的第一性原理是降低接入成本，不是覆盖所有场景。
