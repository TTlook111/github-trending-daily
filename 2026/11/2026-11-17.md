📖 项目是干什么的

Superpowers 不是单条技能，而是给编码 Agent 的一整套**软件开发方法论**，建在一批可组合技能与一段初始指令之上——那段指令的作用是保证 Agent 真的会去加载这些技能。它的起点很有意思：Agent 一看到你在「造东西」，不会立刻动手写代码，而是先退一步问你到底想解决什么；把 spec 从对话里逼出来之后，分段展示给你签字，每一段都短到能真正读完；设计通过后才生成实施计划。

这份计划还带一个很硬的可执行标准：**「一个热情但品味差、没有判断力、没有项目背景、还讨厌写测试的初级工程师也能照着做」**。里面强调真·红绿 TDD、YAGNI（你不会需要它）与 DRY。等你说「go」，它切进 subagent-driven development——由子 Agent 逐个任务实现、检查、评审、继续推进；README 里提到 Agent 常常能连续自主工作几个小时而不偏离你们一起定下的计划。

今天它能冲到第一，安装面的宽度是重要原因：Claude Code 走官方插件市场 `/plugin install superpowers@claude-plugins-official`，另有 Codex App / CLI、Cursor、Devin CLI、Factory Droid、Gemini CLI、GitHub Copilot CLI、Grok Build CLI、Kimi Code、OpenCode、Pi、Qwen Code、Hermes Agent、Muse、Antigravity 各自的安装路径。技能是自动触发的，用户不需要记住命令名——「装上就生效」这四个字，就是它最强的分发能力。

💡 可借鉴的优点

- **产品思维**：卖的不是「能力」而是「纪律」。它解决的从来不是「Agent 不会写代码」，而是「Agent 不受流程约束」；把返工成本前置到 spec 阶段，是这类产品最有价值的位置。
- **架构设计**：可组合技能 + 触发式加载 + 一条串起全流程的初始指令；subagent-driven development 把实现细节隔离在子会话里，主对话只负责决策与验收，上下文不被污染。
- **工程化**：把「计划好不好」翻译成一个可检验的标准（初级工程师能否照着做），比写十条「请仔细思考」有用得多。
- **社区运营**：官方市场 + 自建市场双通道并行，企业侧还留了商业支持入口，开源与商业的分工很清楚。

🌟 特别亮眼的地方

今天这份榜单里，Superpowers 是个「元项目」：另外九个至少有五个在做技能、编排或评审，而它直接定义**技能该怎么被组织成一条可信的开发流程**。当技能数量从几十条涨到几百条（ECC 的 327 条、BugHunter 的 83 条），真正稀缺的已经不是技能本身，而是「什么时候该加载哪一条」的调度逻辑。318K 星证明的不是内容多好，而是「方法论可以被安装」这件事被市场认了。

📖 项目是干什么的

Univer 是一个 Office SDK，目标是在**你自己的产品里造一个 Office**：把电子表格、文档、演示、关系表、画布、PDF 的编辑、计算、协作与文件处理嵌进应用——给人用，也给 Agent 用，用的是你的数据和你的权限。

它拆成三块：**Web SDK** 是地基，包含内容模型与快照格式、插件与依赖管理、命令系统、公式与渲染引擎、Facade API、UI 基础，既能拼成嵌入式编辑器，也能 headless 复用同一套模型做无界面处理；**Server SDK** 负责实时协作、编辑历史与 Office 文件导入导出；**AI SDK** 把 Office 能力接给现有 Agent 与工作流，带内容工具、执行与评审集成。开源的是 Web SDK 的核心架构与引擎（Apache-2.0），商业插件、Server SDK 与 AI 扩展单独授权，功能对照表公开得很清楚。

今天它从昨天的 +988 直接翻到 +1,828，连续两天累计净增接近 2,800。技术难点也确实在这个数字背后：跨特性编辑与撤销。比如在筛选范围内插入一行，会同时改动本体内容与筛选范围，撤销必须把两者一起还原；每个特性各自提供变更与撤销数据，再由命令系统组合执行与记录历史。开源基础还能 headless 跑——在 Node.js 里复用同一套插件、模型、命令和计算做编辑、快照与自动化任务；快速上手只要一个预设，就能拿到完整的表格编辑器。

💡 可借鉴的优点

- **产品思维**：把 Office 当 SDK 而不是产品卖，抢的不是 Excel 的用户，而是「想在自己产品里塞一个表格」的团队；同时把「可被 Agent 调用」写成一等能力。
- **架构设计**：插件 + 依赖注入 + 命令/撤销系统，把「实现一个功能」和「组合多个功能」彻底分开；Facade API 让人和 Agent 用同一套门面。
- **工程化**：开源与商业的边界用功能对照表公开，避免「先用后付费」的信任崩塌；快速上手只装 Sheets Core 预设，不逼你一次吃下全部能力。
- **社区运营**：八种语言 README、Showcase、Discord、Workspace 参考应用、CLI 与 agent skills，把「这东西能长成什么样」直接演示出来。

🌟 特别亮眼的地方

昨天这份日报写的是「审阅是成本，产出才是收益」，今天 univer 用翻倍的增幅补了个更硬的证据：**Agent 办公的瓶颈不在生成，而在「生成完之后能不能被真实编辑系统接住」**。一段 Markdown 谁都能写，但一份能被公式计算、能被多人协同编辑、能一步步撤销的表格，背后是十几年积累的电子表格工程。Agent 越能干，这种「可被接住的载体」就越值钱。

📖 项目是干什么的

这是一个面向**授权范围内的漏洞挖掘与外网红队**的 Claude 技能包。装一次之后，Claude Code 会从「一个聊天机器人」变成「按资深漏洞研究员的习惯工作」：知道该按什么顺序测、该盯哪些类别、怎么把结果整理成能交付的报告，以及最重要的——**始终待在授权范围里**。

体量是它最大的卖点：83 个技能、15 个斜杠命令、681 条来自已披露漏洞报告的模式（其中 433 条逐条标注了出处、可单独审计），覆盖 24 类核心漏洞；另外带企业身份与基础设施的攻击面矩阵、一次性建好的 engagement 目录脚手架、以及 Burp MCP 集成。README 明确写了适用边界：经过授权的红队与漏洞挖掘项目，以及 DVWA、OWASP Juice Shop、Hacker101、testphp.vulnweb.com 这类公开练习靶场。

结构分四层，层层对应一件真实的事：**Think**（方法论 + 红队心态：五阶段非线性流程与批判性思维框架）、**Hunt webapps**（58 个 hunt-* 技能，按漏洞类别组织检测模式、绕过表与组合链模板）、**Hit the perimeter**（M365/Entra、Okta、vCenter、SSL-VPN、SharePoint、云 IAM 等企业平台，2024–2026 年的 CVE 组合链与拿到凭据后的横向路径）、**Ship it**（分诊校验 + 报告 + 证据卫生：七问门、VRT 严重度映射、误报反驳、PII 脱敏）。全部按话题自动触发，不用记技能名。

💡 可借鉴的优点

- **产品思维**：打包的不是「工具集」，而是「资深研究员的判断顺序」。扫描器人人能装，真正贵的是「先测什么、什么时候停、什么该写进报告」。

- **社区运营**：授权范围写在 README 最前面，配合公开靶场做验证，这是这类敏感技能唯一能建立信任的方式。

🌟 特别亮眼的地方

它说明技能正在从「通用能力」走向「职业能力」：当一个 Agent 装上 83 条由真实报告蒸馏出来的技能，它模仿的不再是「会写代码的人」，而是**某个具体职业的人**。这也顺手抬高了这类项目的门槛——不在「能不能跑」，而在「有没有出处、有没有边界、有没有交付标准」。那 433 条逐条标注的引用，才是它敢开源、敢被审计的底气。

📖 项目是干什么的

昨天还是 +423，今天 +1,020，一天之内翻了一倍多。定位没变：腾讯开源的自托管工作台，让团队**用编码 Agent 交付软件**，而不是用 Agent 做演示。你在聊天里描述需求，Main Bot 就会开一个 Docker 沙箱、检出你的仓库、把活派给项目角色，最后开出 PR；当某套工作方式被验证可行，就把它存成 SOP——一套 agent、脚本与人工闸门组成的标准流程，下一个需求照同一条路径交付。

它给了两种工作方式：**跟 Main Bot 聊**，适合探索、快速修 bug、边聊边改；**跑 SOP**，适合固定阶段 + 签核的重复交付。引擎按顺序执行四类节点——Agent 节点、Script 节点、Human-gate 节点、子 SOP 节点，每类都在自己的沙箱里跑。人的控制点给得很细：可以在 Agent 回复中途排队或直接接管消息，可以暂停、恢复、从任意节点重跑，也可以在闸门处把活打回指定步骤。

真正干活的是现成的编码 CLI——CodeBuddy、Codex、Claude Code、OpenCode、Cursor CLI、Antigravity、Kimi Code、Pi、DeepSeek Harness、ZCode 十家。LoopForge 自己补的是它们缺的那一圈：角色、沙箱、检查点、历史，以及「需求—变更」的追踪——聊天路径和 SOP 路径产生的改动都会挂回同一条需求，计入交付与成本报表。Go 写的，MIT 许可，内置后端、前端、bug 修复、产品四套 SOP 模板。

💡 可借鉴的优点

- **产品思维**：把「可复现」当产品。它不承诺让 Agent 更快，只承诺让每次交付都走同一条路——这恰好是团队敢把 Agent 放进真实交付的前提。
- **架构设计**：节点化流程引擎 + 每节点独立沙箱，把流程编排和权限隔离做成同一套东西，而不是两个模块硬拼。
- **工程化**：检查点、任意节点重跑、按需求归集成本，这三项听起来平常，却是「出问题能回退」的全部资本。
- **社区运营**：双语 README、80 秒带声产品演示、内置模板与 FAQ，把「从零设计流程」的冷启动成本压到很低。

🌟 特别亮眼的地方

一天翻倍，说明「SOP」这个词开始被市场认了。昨天它还是「人工闸门是一等节点」的设计亮点，今天已经变成「内置四套模板 + 任意节点重跑」的可用产品。**流程类产品的拐点，通常出现在它开始自带模板的时候**——因为这意味着作者已经把「一套好流程长什么样」想清楚了，用户不必从白纸开始。

📖 项目是干什么的

阿里内部「官方 AI 代码审查助手」的开源版：在内部跑了两年、服务过数万开发者、筛出过数百万条缺陷之后才孵化出来。装完得到 `ocr` 命令，配一个模型端点即可用。工作方式是读 Git diff，把变更文件交给具备工具调用能力的 Agent——Agent 可以读完整文件、检索代码库、看其它变更文件拿上下文，输出**行级精度**的评审意见；`ocr scan` 还能对整个文件做审计，适合接手陌生代码库或没有实质 diff 的目录。

它真正的差异点在架构：**确定性的工程逻辑 × Agent**。不该出错的交给代码——精确文件筛选（哪些必审、哪些过滤）、智能文件打包（例如 `message_en.properties` 与 `message_zh.properties` 合成一个评审单元，每个包跑独立子 Agent、各自隔离上下文，天然支持并发）、模板引擎驱动的规则匹配（比纯自然语言规则稳定得多）、独立的评论定位与反思模块；该动态判断的才交给模型。

底气来自自建的 AACR-Bench：50 个热门开源仓库、200 个真实 PR、10 种语言、80+ 资深工程师交叉标注出 1,505 条 ground truth，数据集放在 Hugging Face 上。官方口径是同一底座模型下 Precision 与 F1 明显高于通用 Agent，token 消耗约为其 1/9，代价是 Recall 更低——**主动取舍，宁可少报也不制造噪声**。今天 +951，比昨天的 +691 又上了一档。

💡 可借鉴的优点

- **产品思维**：不跟通用 Agent 抢「全能」，直接承认纯语言驱动缺硬约束，用工程把底线兜住。
- **架构设计**：文件打包 + 隔离子 Agent 的「分而治之」，是超大 changeset 下还能保持稳定的关键；定位与反思两个模块独立出来，等于承认「评论位置错了比漏报更伤信任」。
- **工程化**：自建 benchmark 并把质量拆成 F1 / Precision / Recall / 耗时 / token 五个可测指标，让「评审水平」第一次可以被复算。
- **社区运营**：多语言 README、npm 分发、兼容 OpenAI 与 Anthropic 协议，接入面铺到几乎零成本。

🌟 特别亮眼的地方

昨天它验证的是「精度优先」这个取舍，今天增幅从 691 涨到 951，说明这个取舍被更多团队接受了。它真正稀缺的不是那套混合架构——而是那 1,505 条 ground truth。**评审质量只有能被标注、能被复算，才谈得上「稳定」**；否则再聪明的 Agent 也只是每次给一份不同的意见。

📖 项目是干什么的

AG-UI 是一个开放、轻量、事件式的协议，标准化「AI Agent 怎么连到面向用户的应用」。它要解决的是每个团队都在重复踩的坑：Agent 根本不适配请求/响应模型——它流式吐 token、在回复中途调工具、更新共享状态、停下来等人、还会开子 Agent，而每个框架的实现都不一样。AG-UI 用一条双向事件流替代这些自定义接线：Agent 发出带类型的事件，任何客户端都能渲染，不管这个 Agent 是用哪个框架写的；同一个 Agent 可以同时驱动 Web、移动端、终端和 Slack。

今天是个节点：**AG-UI 1.0 发布，规范稳定冻结，并由 JSON Schema 背书**，TypeScript、Python、.NET 三套 SDK 全部从 schema 生成，且双向向后兼容——0.x 的 Agent 配 1.0 的客户端能用，反过来也行。接入两条路：`npx create-ag-ui-app@latest` 起一个接好 CopilotKit（Next.js）或终端客户端的前端；或者直接讲协议——一个 30 行的 Python Agent 服务加一个 TS 客户端就能看到文字流式滚出来，连 API key 都不需要。

生态分工写得很克制：MCP 给 Agent 工具与上下文，A2A 让 Agent 之间协作，AG-UI 把 Agent 带到用户面前；一个 Agent 常常三件都用，AG-UI 还可以前置代理那些讲 MCP 或 A2A 的 Agent。README 还专门解释了它和 A2UI、MCP Apps 的关系，避免读者把几种协议混为一谈。

💡 可借鉴的优点

- **产品思维**：只定义「Agent 该怎么被看见」，边界收得极小。规范越薄，越容易被所有人采用。
- **架构设计**：1.0 冻结 schema、SDK 由 schema 生成，等于把「约定」升级成了「规范」；向后兼容让存量 0.x 实现不必推倒重来。
- **工程化**：30 行最小实现 + 官方脚手架 + 三语言 SDK，把接入成本压到「复制粘贴改两行」。
- **社区运营**：Docs / Examples / Spec / Discord 四件套，加上与 MCP、A2A 的明确分工，先解决「我要不要用」的疑虑，再谈怎么用。

🌟 特别亮眼的地方

从 0.x 走到 1.0 冻结，是「协议」这种产品最关键的成人礼。它昨天还在第 8 位、+355，今天 +791 升到第 6——**规范一旦冻结，观望的人就会开始接入**，因为大家等的不是更多功能，而是「它不会再变了」这个承诺。这大概是所有基础设施型产品最难给、也最值钱的东西。

Plannotator 是一个跑在本地的浏览器审阅面板：Agent 抛出一个决策、一份计划、一个 HTML 产物，或者刚干完一段活，界面自动在浏览器打开，你在上面标注、评论，再一键把反馈发回去让它接着做。今天的主推是 **Plannotator Inbox**——它给自己的定位是「你和多 Agent 工作之间缺的那层评审」。

- **架构设计**：本地服务 + 浏览器 UI + 插件 / Hook / MCP 三种接入，从 IDE 到纯终端都能覆盖；Inbox 的异步模型把「人」从实时等待里解耦出来。

🌟 特别亮眼的地方

- **产品思维**：把「写论文」这条长链路拆成可并行、可复审的角色，而不是让一个大模型一口气写完——分工才让质量可归因。
- **架构设计**：五个专门 Agent + 反思 Agent，结构接近真实课题组；LaTeX 模板可插拔，意味着「换会议」不用改代码。
- **工程化**：自动评估（autoraters）、模型可切换（Gemini / OpenAI）、原始材料目录与输出目录解耦，方便批量跑和做对比实验。

## 📊 今日趋势洞察

**核心方向：技能供给规模化之后，交付链路开始补课。**

今天榜上第一次出现「四个技能供给侧项目同框」：superpowers 是方法论型（把整条开发流程做成技能包），Claude-BugHunter 是职业型（83 条按真实披露报告蒸馏的攻防技能），ECC 是平台型（327 条技能 + 72 个 Agent + 记忆与安全扫描），stitch-skills 是厂商型（把自家产品翻译成技能）。四种形态同一天出现，说明「技能」这个品类已经彻底分层——不再是「谁写的提示词更好」，而是「谁供给的技能能覆盖一整条职业链路」。而昨天榜上的 SkillEvaluator 提醒的质检问题，今天依然没有第二个项目来回答，这个空位迟早有人补。

**升温领域：编排被当成流程节点，评审变成流程里的常态动作。**

LoopForge 从 +423 翻到 +1,020，是今天增幅最大的编排项目；open-code-review 从 +691 涨到 +951，plannotator 稳定在 +696。三个项目分别对应流程里的三个位置——谁来执行、谁来验收、谁在中间说话。值得注意的是它们的设计共识：都是「异步 + 可回退」——LoopForge 能从任意节点重跑，open-code-review 宁可少报也不制造噪声，plannotator 干脆不挂起会话。**没有人再试图让人「全程盯着」Agent 了，大家都在设计「人不在场时系统怎么不出事」。**

**接口与载体：协议冻结，产出落地。**

ag-ui 在 1.0 冻结当天 +791，说明基础设施型产品的增长拐点往往不是功能上线，而是「不会再变」的承诺；univer 连续两天累计近 +2,800，则是另一头的证据——活干完得有能被真实编辑系统接住的载体。一个定的是「过程怎么被看见」，一个定的是「结果怎么被保存」，恰好是 Agent 产品化的两端。

**对开发者的三点启发。**

第一，**技能库的瓶颈已经不是数量，是调度**：ECC 的 327 条、BugHunter 的 83 条、superpowers 的一整套流程，真正决定效果的是「加载哪一条、什么时候卸载、冲突了怎么办」；自己攒技能目录时，先写清触发条件与退出条件，比再多写十条更有用。第二，**把评审做成流程节点，而不是最后一关**：open-code-review 的 Precision/Recall 取舍说明，评审工具的价值在于「可预期的噪声水平」，而 plannotator 的异步收件箱说明，人的介入要能在任意时刻发生、且不阻塞任何人。第三，**给产出找载体**：Markdown 是最容易生成、也最容易被丢弃的格式；一旦产出要被人继续编辑、协同、审计，就得接进像 univer 这样的真实编辑系统——**能被接着改的东西，才算交付**。
