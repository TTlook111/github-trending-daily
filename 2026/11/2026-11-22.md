📖 项目是干什么的

Firecrawl 的定位已经从「网页抓取 API」换成「让 Agent 更聪明的知识基础设施」，并且把部署形态拆成了三份。**Firecrawl Local** 是一个 Rust 二进制，`cargo install firecrawl-local` 装上就能在本机 scrape / crawl / map，用你系统里已有的 Chrome 渲染 JS 页面，PDF 与 Office 文档也在本地解析；`init` 能自动把 MCP 服务接进 Claude Code、Claude Desktop、Cursor、Windsurf、Gemini CLI、Codex 六种宿主，并且先备份每一份配置；`serve` 在 3002 端口跑一份兼容 v2 的 API，现有 SDK 改个地址就能用。

**Firecrawl Cloud** 提供规模化版本：96% 的网页覆盖率、P95 延迟 3.4 秒、结构化 JSON / 截图 / 浏览器动作，外加 Search 与 Alexandria——一个打包了 550 多家数据源的知识库；免登录每月 1,000 次额度。**Self-hosting** 则把 `apps/api` 的队列、worker 与数据库整套搬到自己的基础设施上。抓取、爬取、映射跑在本地；需要搜索、Alexandria、Interact、Agent、Monitor 时走云端；`FIRECRAWL_CLOUD=off` 还能强制全部留在本机。

今天它拿到 +1,006，名次稳在第 2。对一个 206,210 星的成熟项目来说，这个数字不是「被发现」，而是「被持续使用」——本地版把隐私与延迟敏感的场景兜住了，云端版把规模兜住了，两条腿都在往前迈。

💡 可借鉴的优点

- **产品思维**：把「给 Agent 供数据」做成独立生意，并用「本地免费 + 云端按量」分层。本地版不是阉割版，而是先把隐私与延迟敏感的场景兜住。
- **架构设计**：本地与云共用同一套 API 契约，代码可平移、SDK 不用重写；`init` 自动识别六种宿主并写配置、先备份，这种「零摩擦接入」比写十页文档有效。
- **工程化**：公开 benchmark 说清覆盖率与 P95 延迟，而不是只说「快」；本地渲染复用系统 Chrome 而不是自带一个浏览器；云端调用失败会标注 `source: firecrawl-cloud`，来源不糊弄。
- **社区运营**：多语言 SDK、playground、Discord 与 X / LinkedIn 三条反馈渠道；免费额度不要求注册，先把「试一下」的门槛降到零。

🌟 特别亮眼的地方

在一个前十换了两张脸的周日，它是唯一一个位置没动、增量没动的项目。这本身说明一件事：**数据供给层已经变成基础设施，而不是热点。** 技能类项目靠新鲜感起量，数据类项目靠「每天真的在用」活下来——模型能力趋同之后，谁能提供更干净、更新鲜、更可追溯的上下文，谁就决定了输出质量的上限。技能决定下限，数据决定上限。

📖 项目是干什么的

Superpowers 卖的不是单条技能，而是一整套**给编码 Agent 装上的软件开发方法论**：一批可组合的技能，加上一段保证「Agent 真的会去加载它们」的引导指令。Agent 判断你在造东西之后不会立刻写代码，而是先退一步问你到底想解决什么；把 spec 从对话里逼出来，分段展示给你确认，每段都短到能真正读完；设计签字才进入计划环节。

计划环节的要求很硬——「一个热情但品味差、没有判断力、没有项目背景、还讨厌写测试的初级工程师也能照着做」，每个任务 2–5 分钟，写清文件路径、完整代码和验证步骤。落地时两套模式二选一：`subagent-driven-development` 每个任务派一个新子 Agent，做完立刻两段式评审；`executing-plans` 则在当前会话内逐条实现，最后统一评审整个分支。工作流被写成七步：brainstorming → git worktrees → writing-plans → 子 Agent 执行 → 红绿 TDD → 代码评审 → 收尾分支。

安装面依旧是它的护城河：Claude Code（官方插件市场）、Codex App / CLI、Cursor、Antigravity、Gemini CLI、GitHub Copilot CLI、Grok Build CLI、Kimi Code、OpenCode、Pi、Qwen Code、Hermes Agent、Muse、Devin CLI、Factory Droid——**16 个 harness，一套技能**。MIT 协议，作者是 Jesse Vincent 与 Prime Radiant 团队。

💡 可借鉴的优点

- **产品思维**：它不卖「能力」，卖「流程」和「否决权」。TDD 技能会删掉那些先写实现、后补测试的代码；评审技能把 Critical 问题设为硬阻断。
- **架构设计**：技能之间用「触发时机」串成流水线，而不是靠一张总提示词硬压；引导技能在会话启动时注入，压缩上下文后再注入一次。技能可组合、可单装。
- **工程化**：技能行为用 drill eval harness（superpowers-evals）做回归测试，插件基础设施另有 `tests/` 与 `npm test`；连「会话跑歪了怎么办」都有 `diagnosing-superpowers` 去读会话记录、给出行级证据、打包脱敏报告。
- **社区运营**：明确不接受新技能投稿、只接受跨 harness 的修改，且不接受「替别人修 issue」的 Agent PR——用规则守住了质量下限。

🌟 特别亮眼的地方

323,732 星、+883、第 3——它已经不是「新项目」了。对一个方法论类项目来说，这种不涨不跌的状态恰恰是成熟的标志：不再靠脉冲，而是变成日常工具的一部分。更有意思的是，它和今天两位新面孔构成一组对照：ponytail 用一条规则让代理少写代码，superpowers 用七步流程让代理按顺序写代码。**一个做减法，一个做顺序，都是同一件事——不信任代理的默认行为。**

| 📦 分类 | 系统互操作 / 二进制移植与兼容 |

📖 项目是干什么的

AnyPS5 是一个把可执行文件自动移植到 Linux 和 Windows 的工具，并且明确**不做模拟器**。它的核心是一个 relinker：把 PS5 可执行文件转换成目标系统的原生格式，再配上一套为动态链接准备的 system prx 库实现（放在 `core/libs/prx`）。README 第一句就写清「No emulation or separate runtime process」——没有模拟层，也没有独立运行时进程，跑起来就是原生二进制。

图形侧有一个着色器重编译器，能把参考着色器形式解码并产出 SPIR-V，编译时打开 `ANYPS5_ENABLE_SPIRV_TOOLS` 还会用 Spirv-Tools 校验产物。输入靠 SDL 映射手柄（含摇杆与扳机），键鼠可以在 `anyps5-input.ini` 里配置。遇到不支持或意外状态，代码统一抛 C++ 异常（通常是 `std::runtime_error`），没人接住就把 `what()` 打到 stderr 并退出——这是移植项目里少见的「失败要说得清楚」。

它的透明程度值得单独说：仓库首页挂着一张进度地图，徽章分别显示系统库覆盖率（明确注明是「项目目前已知函数」的比例，不是 PS5 全部系统函数）、RDNA2 与 gfx1013 参考着色器形式解码进度，以及「7 天内实现」的时间线；分享一个 Web 转换器，文件留在本地；提供 13 种语言的 README；兼容状态按游戏标题在 Discussions 里一个标题一个线程地跟踪。GPL-2.0-only，并声明不包含、不分发、不要求任何版权软件、固件、密钥或专有库，与 Sony 无关联。

💡 可借鉴的优点

- **产品思维**：把自己定位成互操作 / 研究 / 存档工具，而不是模拟器——这个定位既划清了法律与风险边界，也决定了技术路线（重链接而不是模拟）。
- **架构设计**：转换层（relinker）与库实现层（prx）分离，着色器重编译、输入映射、异常处理各自独立；relinker-only 构建能在 macOS（含 Apple silicon）上跑，把「转换」和「运行」解耦成两个可独立验证的环节。
- **工程化**：SPIR-V 产物要过 Spirv-Tools 校验；异常类型统一、失败有明确出口；进度用可刷新的徽章与进度地图量化，而不是「大概能跑了」。
- **社区运营**：13 种语言 README 直接扩到非英语用户；兼容性靠分标题的 Discussions 线程维护，比一个巨大的兼容表更容易协作；免责声明写在正文而不是藏进 LICENSE。

🌟 特别亮眼的地方

它是今天「克制」这条主线的另一半：**新面孔不靠加功能上位，靠划边界上位。** 不模拟、不内置运行时、不分发版权内容、不承诺「全兼容」，把能做的事缩到一条可验证的路线上，然后用进度徽章把这条路线走得多远讲清楚。对一个 59,655 星的项目来说，+850 不是爆发，是「被越来越多人当作正经工程看待」。使用时仍须自行确保镜像与固件来源合法。

📖 项目是干什么的

Ponytail 把一位「头发扎马尾、戴椭圆眼镜、在公司待得比版本控制还久」的资深工程师塞进了 AI Agent：你给他看五十行，他看完不说话，替换成一行。它的主张一句话——**最好的代码是你根本没写出来的那段代码。**

不是「越短越好」的口号，而是一把梯子。写代码前先停在第一个成立的台阶：这件事需要存在吗 → 代码库里已经有了吗 → 标准库能做吗 → 平台原生功能能做吗 → 已装的依赖能做吗 → 能不能一行 → 最后才是「最小可用实现 + 一条小测试」。关键在顺序：梯子是在**读懂问题之后**才跑的，先读改动涉及的代码、追真实数据流，再挑台阶——「对方案懒，对阅读从不懒」。

边界写得很清楚：信任边界校验、数据丢失处理、安全、可访问性永远不上砧板；带分支、循环、解析器、金额或安全的逻辑必须留下一条小测试；每条回复结尾说明「跳过了什么、没检查什么、有什么风险」。v5 的基准是在 Claude Code 里同模型同任务对照：39 个任务（含一个真实的 FastAPI + React 仓库）、Opus 5.5、各跑 5 次——代码量 -53%、耗时 -41%、成本 -26%、token -45%，而有风险的逻辑仍有 98% 带测试（不用它时是 68%），Agent 自己的测试能抓住 66% 的注入 bug（不用它时 46%）。六个安全任务（SQL 注入、路径穿越、伪造 token、限流、畸形 CSV 行、缓存）30 次全过。

工程面也不弱：主体就是一个 `skills/ponytail/SKILL.md` 提示词，外加给规则文件宿主用的 `AGENTS.md`；配套 `/ponytail-review`（按「半夜会被叫起来」的标准审 diff，不只审改动本身）、`/ponytail-audit`（全仓排序，告诉你先修哪个）、`/ponytail-debt`（把 `shortcut:` 注释收成账本，别让「以后再说」变成「永远不说」）、`/ponytail-gain`。Claude Code 里还有一条提示词上方的 band，实时显示本次任务花了多少钱、多少 token、多少 Agent 时间、代码复用率、最后一次改动后测试过没过；board 是本地页面，数据默认留在 `~/.config/ponytail/band/`。20 个 Agent 可用，MIT，npm 包 `@dietrichgebert/ponytail`，README 明确只从官方仓库或官方 npm 安装、永不发布 `.exe` / `.dll`。

💡 可借鉴的优点

- **产品思维**：抓住「代理过度生成代码」这个真痛点，用拟人化的资深工程师做定位；一句「He says nothing. He writes one line. It works.」比十页文档好传播。
- **架构设计**：核心只是一个提示词 + 一份规则文件，其余全是适配层（Claude Code 插件、Codex 插件、AGENTS.md 适配器），所以能同时铺到 20 个宿主而不重复实现。
- **工程化**：用同模型、同任务、多轮对照给出代码量、耗时、成本、token、测试覆盖、注入 bug 捕获率的量化基准，还做了盲测（新版对旧版 110:67）——这是「克制」能被验证的关键。
- **社区运营**：把「只从官方渠道安装」「不发可执行文件」写进 README 当防伪；`/ponytail-debt` 把技术债变成可追踪的账本，让「以后再改」有落点。

第一，**把「不做什么」写成可执行规则**：今天所有跑得稳的项目，都有一份明确的否定清单（不模拟、不写多余代码、不碰未授权资产、不承诺过审）。否定清单比能力清单更能定义产品。第二，**不要只看全站日榜**：主榜只有 16 个位置，语言分榜是稳定的补充通道；今天前十里有两个是从分榜补进来的，漏抓就等于漏掉 20%。第三，**增量看曲线，不看单日数字**：老面孔今天的增量全部挤在 +583 到 +1,803 之间，没有大起大落，这种「原地踏步」恰恰是成熟项目的正常状态；真正值得记的是新面孔第一次出现的那一天，以及它第二天还在不在。
