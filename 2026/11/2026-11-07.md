📖 项目是干什么的

这是一个把编码 Agent 变成「安全审计员」的技能，也是 Cloudflare 官方漏洞发现体系（fleet-wide vulnerability harness）的单仓库起点，Cloudflare 还专门为此写过《Build your own vulnerability harness》。它通过编排一组彼此隔离的 Agent，完成一次结构化安全审计，共六个阶段：**侦察**（把架构、信任边界、输入面、既有证据和确定性覆盖范围写进 `architecture.md` 和 `coverage-ledger.json`）、**覆盖驱动的狩猎**（按覆盖账本分派隔离的猎手，并用「覆盖批评者」找缺口）、**候选验证**（每个候选漏洞交给一个全新的验证者，它的任务是设法证伪）、**结构化输出**（把 confirmed、needs_validation、rejected 三类记录写入 `findings.json` 并对照 JSON schema 校验）、**独立记录验证**（再换新 Agent 复核最终的源码断言）、**目标中立报告**（从已验证记录派生 `REPORT.md` 等报告）。

它的工程纪律很严：父 Agent 在每次账本更新后运行零依赖的 `validate-coverage-ledger.cjs`，在第四、五阶段反复运行 `validate-findings.cjs`，两个校验器都自带测试。三种裁决语义清晰——confirmed 必须有完整源码追踪和有界的实际观察结果，needs_validation 只记录确切的未决事实且不定级，rejected 则留档被证伪的候选；对同一仓库的多次运行是增量叠加的，不会把过期或未决工作当作「已覆盖」。技能通过 Skills CLI 安装，Node.js 运行校验器，并要求在 OS 级沙箱里执行目标代码，否则结论一律保持 needs_validation。

💡 可借鉴的优点

- **架构设计**：发现者与验证者强制分离（对抗式验证），并用「覆盖账本」保证审计不遗漏——这是把安全专家的方法论固化成 Agent 流程的范本。
- **工程化**：零依赖校验器 + JSON schema + 自带测试，让每一步结论都可机器校验、可复现，而非靠模型自觉。
- **产品思维**：用三档裁决精确区分「已证实、待验证、已证伪」，避免模型在证据不足时草率下结论，非常克制。
- **安全设计**：明确要求沙箱断网、环境白名单、资源限额、写入受限，把「审计工具自身不能成为攻击面」写进硬性要求。

🌟 特别亮眼的地方

一个云厂商把内部最核心的安全能力抽象成可安装、可审计的开源技能，这本身就是强信号：**安全正在从「专家的手工活」变成「Agent 可重复执行的标准流程」。** 它的六阶段模型和覆盖账本思路，不只适用于安全，任何需要高可靠、可追溯结论的复杂审查（合规、性能、代码评审）都能借鉴。

📖 项目是干什么的

OpenMausBot 是一个开源的「Grok Bot 替代品」，核心理念是：**「一个盒子里一个助手」对 Agent 来说是错误的形态**。Agent 应该像聊天软件里的联系人——侧边栏一排 Bot，每个都有自己的人格、记忆、模型、电脑和已连接应用，你跟它们聊天、看它们干活、在关键动作上点「批准」。README 直接把自己定位为近期几款闭源个人 Agent 产品的开源对应物，并逐一列出差异。

实现上它坚持「自带 Agent、本地优先」：Bot 底层跑的是你本机已安装的 claude / codex / grok CLI，沿用现有登录和订阅，中间没有代理；一个监听 127.0.0.1 的小型 harness 服务管理所有 Agent 进程，转录、密钥、事件都存在 `~/.openmausbot`。每个 Bot 可使用云端 Linux 桌面、隔离的本地 VM，或在明确开启后控制你自己的电脑；通过 Composio 连接 500+ 应用。Shell 命令、文件编辑等风险动作以内联卡片请求 Allow / Deny，由统一的「权限代理」裁决。桌面端基于 Electron，移动端用 Expo，Apache-2.0 许可，并特别声明没有发行任何代币。

💡 可借鉴的优点

- **产品思维**：用「聊天软件 + 联系人」这个所有人都熟悉的隐喻管理多个 Agent，学习成本几乎为零，把多 Agent 从工程概念变成日常交互。
- **架构设计**：不自己接模型，而是编排用户已有的 Agent CLI——复用现有订阅，也避开了「再托管一层 API Key」的信任问题。
- **安全设计**：所有风险动作走统一权限代理并以审批卡片呈现，密钥「只写不读」，控制本机需显式开启。
- **增长打法**：README 系统化地做「X 的开源替代」对比页，精准承接搜索流量，是开源项目 SEO 的教科书式操作。

🌟 特别亮眼的地方

OpenMausBot 抓住了「Agent 从对话框变成团队」这个产品形态，它最可借鉴的是「编排而非替代」——不跟大厂拼模型，而是站在用户已有的 CLI 之上做组织、权限和工位，把「模型、电脑、数据都在厂商那边」翻转成「都在你这边」。

📖 项目是干什么的

Sherlock 是一个 2018 年诞生、至今仍在活跃维护的开源情报（OSINT）工具，做的事情一句话讲清：**给定一个用户名，在 400+ 社交网络上搜索同名账号是否存在**。它逐个请求各站点的用户主页，根据返回状态判断账号是否被注册，把找到的账号连同链接汇总输出到文本、CSV、XLSX 或 JSON 文件，是安全研究、品牌保护和个人足迹排查的常用工具。

工程上它已经迭代到 0.16.0，默认分支为 master，安装方式覆盖 pipx、uv、Docker、dnf 以及多个社区维护的系统包，并对失效的第三方包（如 ParrotOS、Ubuntu 24.04 的包）主动在 README 给出警告。命令行支持多用户名、代理、超时、站点限定、NSFW 站点过滤、本地 `data.json` 离线运行等，站点清单本身是一个可独立更新的 JSON，这让它能持续跟上社交网站的变化。

💡 可借鉴的优点

- **架构设计**：把「站点规则」与「检测逻辑」解耦——站点清单是数据文件、核心引擎只读数据，新增站点无需改代码，是规则引擎的经典结构。
- **工程化**：提供 pipx/Docker/系统包等多渠道安装，并对已知失效的分发包显式预警，文档对兼容性极其诚实。
- **产品思维**：一个极窄的需求（查同名账号）做深做透、覆盖 400+ 站点，靠长期维护积累起近 10 万 star。
- **可扩展性**：支持 `--json` 加载自定义站点清单，让工具能被二次集成而非只能命令行使用。

🌟 特别亮眼的地方

一个 2018 年的「老工具」在 Agent 时代重新冲上日榜，说明**成熟、可靠、可脚本化的基础工具正在被新一波自动化场景重新估价**。它的数据驱动站点清单设计，今天看来依然是做「可插拔规则平台」的优秀范本；对 Agent 开发者而言，这种稳定工具也正是最适合被 Agent 调用的「原子能力」。

📖 项目是干什么的

agent-browser 是 Vercel Labs 推出的原生 Rust CLI，给 AI Agent 一个能逐条命令驱动的浏览器。它的核心交互是**「快照 + 引用编号」**：`snapshot` 把页面读成紧凑的文本，每个可交互元素带一个类似 `@e1` 的引用；Agent 基于引用执行点击、填写，再重新读页确认结果，如此循环。浏览器在命令之间保持开启，每一步都是一次很短的 shell 调用，无需把整个页面塞进上下文。

它的工作方式是：首个命令启动后台 daemon，通过 Chrome DevTools Protocol 控制浏览器，每个 `--session` 有独立的 daemon 和浏览器，默认一小时无操作自动关闭。默认用 Chrome for Testing，也可用 `--cdp` 接入已运行的 Chrome，用 `--engine` 切换 Lightpanda、Obscura 等引擎，支持 iOS 模拟器里的 Mobile Safari 和多家云浏览器（Browserbase、Browserless 等）。CLI 还随版本自带匹配的技能（`agent-browser skills get core`），并提供 `mcp` 子命令启动 MCP server，Apache-2.0 许可。

💡 可借鉴的优点

- **产品思维**：用「快照引用」而不是截图或完整 DOM 与 Agent 交互，极大节省 token，且每次操作后强制重读确认，天然闭环。
- **架构设计**：daemon 常驻 + 会话隔离 + 协议解耦（CDP），并兼容多种浏览器引擎和云服务，扩展性强。
- **工程化**：点击在元素被遮挡、禁用、不可见时会明确失败而非假成功，把「不可靠操作」显式暴露。
- **生态策略**：自带版本匹配的技能和 MCP server，让任何 Agent 宿主都能接入，且技能指令始终与已装 CLI 一致。

🌟 特别亮眼的地方

它代表了 Agent 浏览器自动化的一个务实流派：**不追求让 Agent「看懂」一张图，而是把页面结构化、把动作编号化，用最小的上下文开销换最高的确定性。** 与今天 #1 的安全审计、#10 的上下文压缩一样，都在解决同一件事——让 Agent 的每一步都可靠、可验证、低成本。

📖 项目是干什么的

它的差异化设计很明确：**开放内部**——组件可在任意层级组合，构建块直接导出，需要深入时用 swizzle 把组件完整源码「弹出」到项目里自己拥有；**无样式锁定**——样式用 StyleX 编写但对消费者透明，可用 Tailwind、CSS Modules 或普通 CSS 通过 className 覆盖；**主题即 CSS 变量覆盖**，无需 fork 或包裹组件即可定制；并且**从 API、文档到 CLI 都按「人和 Agent 用同一套方式构建」来设计**，配套 Storybook、沙箱和完整文档。

💡 可借鉴的优点

- **产品思维**：明确「引导而非强制」——组件给能力而不是设护栏和用户对抗，设计主张放在文档里。
- **工程化**：强约定（命名、props、组合规则统一）+ 完整文档 + CLI，让人和 AI 都能预测陌生组件的行为。
- **生态策略**：Meta 把内部标准对外开放，同时兼容主流样式工具，降低采用门槛。

🌟 特别亮眼的地方

Astryx 最值得注意的是它把「Agent 就绪」写进设计初衷——**当 AI 开始大量生成界面，设计系统的价值不只是给人用，更是给 Agent 提供一套可靠、可预测、可组合的组件语言。** 它和今天 #5、#7 一起，勾勒出「人机共用一套标准」的工程方向。

📖 项目是干什么的

billion-context 是一个上下文压缩插件，目标是让单个会话能持续一个月、累计十亿级 token，同时保持小上下文窗口（100K 足够）并节省约 5 倍 token，且不牺牲压缩质量。它适配 Claude Code、Codex、OpenCode、Gemini CLI、Qwen、Copilot、Zed 等 20 多种编码 Agent，提供 npm 全局安装，并配有学术预印本阐述其「模型驱动的增量分层压缩、无需训练的多代上下文管理」方法。

它的工程关注点很细：健康会话应保持 **95–97% 的前缀缓存命中率**，压缩本身的开销不超过 2%，并提供命令排查缓存归因（常见原因是上游缓存 TTL 过期、模型切换等）；默认分支为 master，提供中英文文档、QQ 社区和完整 FAQ。本质上它解决的是长周期 Agent 的核心难题——如何在有限窗口里既保留关键信息、又不反复为旧上下文付费。

💡 可借鉴的优点

- **架构设计**：增量、分层、多代压缩而非一次性重写，配合前缀缓存最大化，是长上下文管理的工程化方案。
- **工程化**：把缓存命中率这种关键指标显式量化（95–97%）并提供排查工具，让压缩效果可观测、可诊断。
- **产品思维**：一个插件横向兼容 20+ Agent 宿主，不绑定生态，靠通用价值获客。
- **严谨性**：用预印本沉淀方法论，区分「压缩开销」与「缓存收益」，口径清晰。

🌟 特别亮眼的地方

上下文工程正在成为 Agent 可靠性的关键一环，而它的价值主张很务实：**不靠更大的模型窗口，而靠更聪明的压缩和缓存，让长会话既省钱又不丢记忆。** 与今天 #5 的浏览器快照、#1 的可审计流程一样，都是在「让 Agent 长期、低成本、可信赖地工作」这条主线上的关键拼图。

**核心方向：Agent 技能标准化，平台级大厂集体入场——竞争从「拼模型」转向「拼技能生态」。**
