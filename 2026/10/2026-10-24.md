## 总览摘要

今天的榜单仍然是一张「Agent 工程化」的拼图，但重心比前几天更明确地落到了**「如何把编码 Agent 变得更专业、更安全、更会审美」**这件事上。榜首不是某个新模型，也不是又一个 Agent 框架，而是一批**「技能（Skill）」**——给已有的编码 Agent 喂进某个垂直领域的专业判断力：Cloudflare 把自己的漏洞挖掘流程开源成一个安全审计技能（#2），Together AI 和独立开发者各自做了「反 AI 味」的设计技能（#4、#6），还有一份把 Claude Code 讲透的可视化教程（#1）。它们共同说明：当通用模型的底座趋于同质，差异化开始来自**「挂在模型外面的那层领域知识」**。

第二条主线是 **Agent 运行时的安全与隔离**。NVIDIA 下场做 OpenShell（#2），用内核级策略 + 形式化验证给自主 Agent 套上「只能碰被授权的东西」的笼子；AWS 则把官方 MCP 服务、技能和插件打包成 Agent Toolkit（#3），用 IAM 条件键区分「人的操作」和「Agent 的操作」。两家云厂商不约而同地在回答同一个问题：**当 Agent 能自己跑命令、调 API、用凭证时，怎么让它既有用又不越权**。

此外，本地优先与开源基础设施的老主线依旧在：pollen-robotics 把一只用强化学习走路的小鸭机器人完整开源（#7），Google 的 gemini-cli（#8）、一份中文电子书索引库（#9）和实时分析数据库 ClickHouse（#10）各自代表了终端 Agent、知识聚合与数据底座的持续热度。把这 10 个项目串起来看，今天开发者世界关心的是：**让 Agent 更懂行（技能）、更守规矩（运行时安全）、也更接地气（本地与开源基建）。**

📖 项目是干什么的

claude-howto 想解决一个很多人都有的尴尬：装好了 Claude Code，跑了几条 prompt，然后「然后呢？」——官方文档只讲每个功能是什么，却不教你怎么把斜杠命令、记忆、子代理、hooks、MCP 组合成真正省时间的工作流。这个项目把自己定位成「一个周末精通 Claude Code」的可视化、以示例驱动的教程。

它用 10 个模块覆盖 Claude Code 的全部能力，从斜杠命令、记忆、检查点，到技能、hooks、MCP、子代理、高级特性和插件，并给出带时间估算（总计约 11–13 小时）的渐进式学习路径。每个模块都配 Mermaid 图讲「底层是怎么运作的」，附可直接复制进项目的模板（CLAUDE.md、hook 脚本、MCP 配置、子代理定义、完整插件包），还内置自测：在 Claude Code 里跑 `/self-assessment` 定位自己的水平，跑 `/lesson-quiz` 查漏补缺。

它强调与官方文档「互补而非替代」——文档是功能参考，这里是带图、带模板、带路径的教程，并且跟每次 Claude Code 发布同步（当前对齐 v2.1.302，2026 年 10 月），还提供英、中、越、乌、日多语言版本和可离线阅读的 EPUB。

💡 可借鉴的优点

- **产品思维**：精准打中「功能我都知道，但不会组合」这个痛点，把卖点从「讲功能」换成「讲工作流」——自动代码评审、CI/CD、文档生成等真实用例，每个都标注要组合哪几个功能。
- **工程化**：把教程本身做成「可在 Claude Code 里跑」的东西（自评、测验都是斜杠命令），学习即实操；并用脚本一键生成 EPUB，内容和图表全带。
- **社区运营**：用「渐进路径 + 时间估算 + 自测定级」降低上手焦虑，多语言覆盖进一步扩大受众；MIT 许可、强调「免费永久」。

📖 项目是干什么的

这是 Cloudflare 开源的一个「把你的编码 Agent 变成安全审计员」的技能。它不是一条 prompt，而是一整套**多阶段、互相制衡**的审计流程：侦察（画出架构、信任边界、输入面，并把确定性的覆盖项记进 `coverage-ledger.json`）、按覆盖清单分派隔离的「猎手」去找漏洞、对每个候选交给**全新的验证者去反证**、输出结构化记录（confirmed / needs_validation / rejected 三种判定）、再由独立 Agent 核对最终的源码论据，最后生成目标中立的报告。

它的判定哲学很克制：`confirmed` 必须有完整的源码链路和可观测的边界失效；`needs_validation` 记录一个「还没解决的确切事实」且不给严重度；`rejected` 则是被反证掉的候选。严重度要求「可能性 × 影响」，而不是「偏离某个清单」；纵深防御的缺失只算加固建议、不算漏洞。多次对同一仓库运行是叠加的——用历史账本定位盲区、重验改动过的源码，不把陈旧或未决的工作当成已覆盖。README 坦言：在他们的测试里，单次运行大约只能找到重复多轮累计漏洞的一半。

这个技能正是 Cloudflare 内部漏洞发现系统的「单仓库起点」，用 `npx skills add` 即可装进任意支持技能的编码 Agent，用 Node 跑零依赖的校验脚本，要求一个禁网、受限、只能写指定临时目录的 OS 级沙箱来跑目标代码。

💡 可借鉴的优点

- **架构设计**：「找漏洞的 Agent 永远不是验证它的 Agent」——用对抗式验证（adversarial validation）从机制上压制单个 Agent 的幻觉和过度自信，这套「生成者 / 反证者分离」的模式对任何高风险的 AI 判断都通用。
- **工程化**：用 `coverage-ledger.json` 和 `report-schema.json` 把「查了什么、结论是什么」做成**机器可校验的结构化记录**，再配零依赖校验脚本在流程关键节点自动跑，避免 Agent「自说自话」。
- **安全意识**：强制要求禁网、沙箱、资源限制才允许执行目标代码，否则线索只停留在 `needs_validation`，把「不敢确认就别乱确认」写进流程。
- **诚实度**：公开承认「单次运行只覆盖约一半」，并把多轮叠加做成设计目标，这种对局限的坦诚本身就是可信度。

🌟 特别亮眼的地方

安全审计是最不容忍「AI 瞎编」的场景之一。Cloudflare 的解法不是让模型更聪明，而是用**流程工程**——隔离、分工、反证、结构化记录、独立复核——把不可靠的生成，约束成可审计、可复现、可叠加的结论。它示范了「Agent 技能」能承载的复杂度上限：不是一段提示词，而是一套带状态机、校验器和安全前提的完整方法论。这是「让 Agent 更懂行」这条主线上最硬核的样板。

### #3 NVIDIA/OpenShell ⭐

| ⭐ Stars | 19,148 (+893) |

| 📦 分类 | AI 基础设施 / Agent 运行时与隔离 |

📖 项目是干什么的

OpenShell 是 NVIDIA 做的「给成群自主 Agent 用的安全、私密运行时」。它的出发点很实际：Agent 只有能读文件、装包、调 API、用凭证时才真正有用，但你不想因此把数据、密钥、网络全盘交给它。OpenShell 让你用一份策略声明「每个 Agent 能碰什么」，然后由它来强制执行。

它的执行分两层。**内核级强制**：每个 Agent 跑在隔离沙箱里，内核控制它能访问哪些文件、能发哪些系统调用，每一个网络连接出沙箱前都要过策略检查；Agent 永远看不到真实凭证，OpenShell 只在请求发往被批准的端点时才把凭证加上去。**形式化验证的策略变更**：在一次策略修改被批准前，OpenShell 用形式化验证去标记它会新放开哪些危险访问（比如带着凭证去够一个新主机、调用一个新 API 方法），这类变更要等人工审核。

0.1.x 版本带来了稳定的发布节奏、新的隔离原语和更大的扩展面。支持 Linux、Apple Silicon 的 macOS、实验性的 WSL2，用 `curl | sh` 安装 CLI 和本地网关，默认沙箱是不带 Agent 的极简 Ubuntu。它还提供 Python/TypeScript/Go/Rust 多语言 SDK、可用 Helm 部署到 K8s，并把自己「agent-first」——用它所赋能的同一套 Agent 工作流来开发自己。采用 Apache-2.0。

💡 可借鉴的优点

- **架构设计**：把安全做成「运行时强制 + 变更前验证」两道关——前者管「此刻能做什么」，后者管「改了策略之后会多出什么权限」，互补地覆盖了 Agent 权限治理的动态与静态两面。
- **凭证处理**：Agent 全程看不到真实凭证，只有发往授权端点的请求才被注入凭证，这种「凭证与 Agent 解耦」的设计极大缩小了泄露面。
- **工程化**：Rust 实现、内核级 hook、形式化验证、多语言 SDK、K8s 部署、可编译掉遥测——是典型的基础设施级完成度；且遥测明确不采集路径、主机名、prompt、凭证等敏感信息。
- **可信交付**：用「agent-first」自举（自己开发自己），既是能力证明，也让贡献流程天然贴合 Agent 工作流。

🌟 特别亮眼的地方

当 Agent 从「聊天」走向「自己动手跑命令」，最大的风险从「说错话」变成了「做错事」。OpenShell 代表了一种明确的行业判断：**Agent 的安全不该靠模型自觉，而要靠外部运行时强制。** 由 NVIDIA 这样的基础设施厂商下场、用内核级隔离 + 形式化验证来兜底，意味着「自主 Agent 的沙箱」正在从研究概念变成生产级基建。对任何要让 Agent 接触真实系统的团队，这里给出了「最小授权 + 变更前审查」的参考范式。

📖 项目是干什么的

hallmark 是 Together AI 做的、给 Claude Code / Codex / Cursor / OpenCode 用的设计技能，口号直白：**「拒绝看起来像 AI 生成的」**。它先守住一条硬底线，然后就让开：从一个 48 种「材料」的主题库里发三个主题，围绕「访客来这个页面要干什么」来搭页面，再用真实浏览器去 lint 结果，专门揪那些一眼就「机器味」的毛病——每个标题上方都有的小标签、全大写带字距的标签文字、标题里只有一个词变色、一整页空框或全是照片、撑不满屏的 hero、每页结尾都塞的邮件订阅、点了「谢谢」却什么都没提交的假表单。最后还有一个「全新上下文」的审查者下最终结论。

它的门禁分层：**Floor（底线）**绝不放行（对比度、焦点、减少动态、瞎编事实、手机布局崩掉）；**Reflex（反射）**门是模型容易掉进去的默认套路，有正当理由可以在记录在案的前提下推翻；**Finish（收尾）**检查是工艺细节，永不阻塞发布。v2 新增 48 个主题（每个是一种「材料」：纸张、字体、配色、表面、自带组件和纹理，配一张成品图，且每个主题文件 ≤8KB），强调「从任务出发」（订票页会订票、商店会卖货、订阅页会订阅），支持纯 prompt 的自定义页面、指向真实产品 URL 自动截图，以及 755 张开放授权、按主题挑选并在页面署名的真实照片。还能 `/hallmark redesign` 重做一个页面但保留内容和接线、`/hallmark audit` 只报告。MIT 许可。

💡 可借鉴的优点

- **产品思维**：把问题从「生成更好看的设计」反转成「消除会暴露 AI 的特征」——用做减法（约束 / 反模式）而不是加法来提升观感，定位极清晰。
- **架构设计**：「分层门禁」（底线永不放行、反射门可带理由推翻、收尾检查永不阻塞）把「哪些必须守、哪些可权衡、哪些只是锦上添花」讲得很清楚，是一套可迁移的质量闸设计。
- **工程化**：用真实浏览器在 8 种宽度下 lint（`sloplint --render`），再叠一个「全新上下文」的 subagent 复审；redesign 前用 `--before` 记录每个链接/字段/handler，`--kept` 在丢失任何一个时让重做失败——把「别把功能改没了」做成了硬校验。
- **合规意识**：照片只用 Wikimedia Commons 的开放授权图并逐一署名，明确不碰 Unsplash/Pexels（其条款禁止 AI 工具选图）。

🌟 特别亮眼的地方

「AI 味」正在成为一个真实的产品问题——同样的模板、同样的紫蓝渐变、同样的卡套卡，让 AI 生成的前端有了一眼可辨的「塑料感」。hallmark 的价值在于把「审美判断」拆成了**可检测的反模式 + 可记录的例外 + 可复核的终审**，让「好看」这种主观的东西有了工程化的闸门。它和同类的 impeccable（#6）一起说明：设计正在成为编码 Agent 下一个要被「技能化」的专业领域。

📖 项目是干什么的

这是 AWS 官方支持的 Agent Toolkit，目标是给 AI 编码 Agent「在 AWS 上构建、部署、运维应用」所需的工具、知识和护栏。它开箱适配开发者已经在用的 Agent——Claude Code、Codex、Cursor、Devin、Kiro、fx 等。

它由三部分组成：**插件（Plugins）**把「AWS MCP 服务配置 + Agent 技能」打包成一次安装，核心是 `aws-core`（服务选型、CDK/CloudFormation、Serverless、容器、存储、可观测性、账单、SDK 用法、部署），还有 `aws-agents`（用 Bedrock/AgentCore 搭 AI Agent）、`aws-data-analytics`（S3 Tables、Glue、Athena 的数据湖/分析/ETL）、`aws-agents-for-devsecops`（事件排查、代码审查、漏洞扫描、渗透测试）和 `aws-startup-advisor`（创业视角的架构、成本、迁移建议）。**技能（Skills）**是按需加载的指令与参考材料包。**AWS MCP 服务**则通过一个认证端点覆盖 300+ AWS 服务，提供沙箱化脚本执行、实时文档检索，以及 CloudWatch 指标、IAM 上下文键、CloudTrail 审计等企业控制。

它明确是 2025 年 AWS Labs 那批 MCP/技能/插件的「继任者」，关键增量是：用 **IAM 条件键区分「Agent 的操作」和「人的操作」**（可以写出「即使用户本身有写权限，经 MCP 的也只允许只读」的策略），每个请求都有 CloudWatch 指标和 CloudTrail 审计，技能经过端到端评测。Apache-2.0。

💡 可借鉴的优点

- **产品思维**：不另造一个 Agent，而是「适配开发者已经在用的全部 Agent」，并用官方 marketplace 分发插件，站在生态而非孤岛的位置。
- **架构设计**：把「MCP 服务 + 技能」解耦——技能不依赖 MCP、MCP 也不服务本地技能，两者互补又能各自独立安装，适配不同 Agent 的落地方式。
- **安全治理**：用 IAM 条件键把「Agent 行为」和「人工行为」在权限层面分开，是企业让 Agent 接触真实云资源时最关键的一道控制；再配审计日志形成闭环。
- **可信度**：技能经过「端到端评测」才发布，并坦诚说明与旧的 AWS Labs 工具的关系与迁移路径，降低了企业采用的顾虑。

🌟 特别亮眼的地方

它和 NVIDIA 的 OpenShell（#3）形成有趣的呼应：都在回答「怎么让 Agent 安全地碰真实系统」，但角度不同——OpenShell 从通用运行时隔离入手，AWS 则从**自家云的 IAM/审计体系**入手，把「Agent 专属权限」做成一等公民。对已经重度使用 AWS 的团队，这意味着不必自建沙箱，就能用熟悉的 IAM + CloudTrail 把编码 Agent 的云操作管起来。它代表了云厂商把 Agent 治理「原生化」进自家控制面的趋势。

📖 项目是干什么的

impeccable 是另一个「让你的 AI harness 更会设计」的技能，和 hallmark（#4）同属今天的「设计技能」阵营，但路线更偏**可确定性检测 + 跨工具通用**。它包含 1 个技能、24 条命令、浏览器内实时迭代，以及 62 条确定性检测规则，专治 AI 生成前端的那些「套路味」。

它的出发点是：所有模型都在同一批 SaaS 模板上训练，于是不加引导就会反复吐出同样的毛病——到处用 Inter、紫到蓝的渐变、卡片里套卡片、彩色背景上的灰字、每个标题上方那个圆角方块图标。impeccable 的做法是：`/impeccable init` 先把「持久的产品真相」（受众、目的、运行场景、约束、语气）写进 `PRODUCT.md`，和表层视觉方向分开记录；24 条命令组成一套共享设计词汇（polish / audit / critique / distill / animate / bolder / quieter 等）；62 条确定性规则加 LLM 专属的评审检查，其中 CLI 和浏览器插件跑确定性规则**不需要 LLM、不需要 API key**。

它最突出的工程特征是**「一次写、处处可用」的极致跨工具支持**：仓库里为 Claude Code、Cursor、Codex、Gemini CLI、Grok、Hermes、OpenCode、Pi、Kiro、Trae、Qoder、Mistral Vibe、DeepSeek Harness、Google Antigravity 等近 20 种 harness 都准备了独立的安装目录和 hook 清单，并能在编辑时自动触发设计检测器。引擎是一个自包含二进制（Rust），`npx impeccable` 只是它的薄壳。Apache-2.0。

💡 可借鉴的优点

- **工程化**：把检测器做成「62 条确定性规则 + 可选 LLM 评审」，确定性部分零 LLM、零 API key，既快又便宜，还能进 CI（`--json` / `--github` 注解、带退出码），把「设计质量」变成可自动化的 lint。
- **架构设计**：用 `PRODUCT.md` 把「持久的产品真相」和「每个页面的视觉方向」解耦，避免把「这个产品是什么」和「这次想要什么风格」搅在一起——是很清醒的信息建模。
- **可移植性**：对近 20 种编码 Agent 做了一等公民支持，并处理了各家 hook/信任模型的差异（Codex 要批准 hook、Hermes 要 trust、Grok 要 folder trust），是「跨 harness 分发」的教科书级案例。
- **隐私**：遥测只记匿名的「发了哪手牌、哪张胜出」，明确不传项目名、文件、代码、`PRODUCT.md`；提供多种关闭开关（`DO_NOT_TRACK` 等）。

🌟 特别亮眼的地方

impeccable 和 hallmark 隔着榜单互为镜像：hallmark 偏「主题库 + 浏览器复审」，impeccable 偏「确定性规则 + 跨工具分发」。它最值得学的是**把主观的「设计好坏」尽可能转成客观、可脚本化的检测**——能确定性判断的绝不喂给 LLM，省钱、可复现、可进 CI。当「反 AI 味」成为共识需求，这种「设计 linter」很可能像代码 linter 一样，成为 Agent 生成前端时的标配前置。

📖 项目是干什么的

microduck 是 Pollen Robotics（现属 Hugging Face 阵营）开源的一只**会走路的小鸭机器人的「大脑」**。本体约 25 厘米高、800 克重，跑在一颗 Rockchip RK3566 上，由一组守护进程以 50Hz 的控制回路、用神经策略驱动 15 个舵机。它会走、会被遥控、会捡东西（喙触地一键拾取）、被推倒能自己站起来，还会坐、踢球、换上轮子进入「滑行模式」，并用自己的嗓音嘎嘎叫。

💡 可借鉴的优点

- **工程化**：更新机制「签名发布 + 健康门禁 + 自动回滚」，专门为「不把机器人刷成砖」设计；守护进程按职责拆分（控制、更新、网络、蓝牙、媒体、深度），边界清晰。
- **可复现**：把「训练在哪、怎么导出、真机怎么加载」讲得明明白白（MuJoCo→PPO→ONNX→robotd），并提供纯仿真模式让没有实体机的人也能开发，极大降低参与门槛。
- **文档文化**：`docs/design/` 记「为什么这么设计」、`docs/project/` 记「出过什么问题、怎么才算解决」，把决策与教训沉淀下来。

🌟 特别亮眼的地方

## 📊 今日趋势洞察

**核心方向：从「造 Agent」转向「让 Agent 更懂行、更守规矩」。**
今天的 10 个项目可以归成三条清晰的线：

- **技能化的专业能力（让 Agent 更懂行）**：claude-howto（#1）教你用好 Claude Code，security-audit-skill（#2）把安全审计流程技能化，hallmark（#4）、impeccable（#6）把设计审美做成可检测的技能。「技能」正在成为给通用模型注入垂直专业判断的主要载体。
- **运行时安全与治理（让 Agent 更守规矩）**：OpenShell（#3）用内核级隔离 + 形式化验证，agent-toolkit-for-aws（#5）用 IAM 条件键 + 审计，两家从不同角度回答「Agent 碰真实系统时如何最小授权」。
- **底座与具身（让 Agent 更接地气）**：gemini-cli（#8）是终端入口，microduck（#7）是开源具身 sim2real，ebook-treasure-chest（#9）是零后端知识索引，ClickHouse（#10）是支撑 AI 应用的实时分析底座。

**升温领域：**
1. **「技能」作为能力分发单位**——越来越多的专业知识（安全、设计、云、教程）被封装成可被多种编码 Agent 复用的 Skill。
2. **Agent 运行时安全**——当 Agent 能自主执行命令/调用凭证，隔离、最小授权、变更前验证、审计成为刚需，云厂商与硬件厂商同时下场。
3. **「反 AI 味」设计工程化**——把主观审美拆成确定性反模式检测 + 可记录例外 + 独立终审，设计 linter 雏形出现。
4. **AI 应用的数据底座**——实时 OLAP、可观测性随 AI 应用一起升温。

**对开发者的启发：**
- 想让 Agent 在某个领域靠谱，不一定要换模型，可以先写一个高质量的「技能」把领域判断喂进去——security-audit-skill 示范了技能能承载的复杂度上限（状态机 + 校验器 + 安全前提）。
- 让 Agent 接触真实系统前，先想清楚「隔离、最小授权、变更前审查、审计」四件事；OpenShell 和 AWS Toolkit 分别给了通用与云原生两套参考。
- 「对抗式验证」（找问题的 Agent ≠ 验证问题的 Agent）是对抗 AI 幻觉的通用招式，可迁移到任何高风险的 AI 判断。
- 把主观质量（设计、文案）尽量转成确定性检测 + 可进 CI 的 lint，能确定判断的就别喂 LLM——省钱、可复现、可自动化。
