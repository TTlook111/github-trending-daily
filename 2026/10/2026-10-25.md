## 总览摘要

和前几天「编码 Agent 技能」刷屏的榜单不同，今天的热榜回到了一种更「朴素」的开发者需求：**把身边一件具体的事做得又快又干净**。排在最前面的两个项目不约而同都在干同一件事——**给电视装一块清爽的桌面**：aerial-tv（#1）给国产 Android TV 做了一个仿 tvOS 的无广告启动器，free-my-tv（#2）则面向 Google TV / LG webOS / 三星 Tizen 做了同样的事，还贴心地留了「一键还原」。两个项目都主打「无广告、无跟踪、开机即接管」，几天内冲上数千 star，说明被厂商预装界面折磨的用户有多想要一块安静的主屏。

第二条线是**安全与逆向**的集中爆发。fairplay-decrypt（#4）做离线的 App Store IPA 解密与独立密钥推导；一组围绕 php2shell（CVE-2026-109618/109619）的 PoC 仓库（以 #5 为代表）在一周内密集出现，把一个 PHP `session.upload_progress` 预认证漏洞的利用链和检测规则摊开来讲；REA-Prompts（#3）则是一套「逆向任何东西」的提示词集。它们共同反映出：当新漏洞披露时，社区的 PoC、检测规则、逆向方法会以极快的速度围绕它聚集。

剩下的项目各自代表一个扎实的工程方向：hatchzip（#6）用「边解压边缩小源文件」解决大压缩包的磁盘占用；wesbos/3d-model-anything（#7）把 iPhone 的 LiDAR + 照片重建成可编辑的 Three.js 房间；reylo（#8）让你把 `.sql` 文件直接 import 进 TypeScript 并自动推断类型；day-trader-skill（#9）是今天仅存的「技能」代表，把日内交易拆成 11 个 Claude 技能；ElyOffice（#10）用 Rust + GPUI 做离线优先的桌面办公套件。把这 10 个串起来看，今天开发者世界关心的是：**把真实、具体的痛点（电视广告、大文件解压、SQL 类型、漏洞复现）用干净的开源工程解决掉。**

📖 项目是干什么的

aerial-tv（Aerial）给国产智能电视做了「一块干净的桌面」：一个参照 tvOS 设计的开源 Android TV 启动器，没有广告、开机自动接管原厂主屏。它的定位非常明确——很多小米、TCL 等国产电视的原生界面塞满了推荐位和广告，Aerial 想把那套花哨、嘈杂的首页换成一个安静、以内容为中心、遥控器友好的主屏。

它的落地方式也很接地气：通过一条 `curl .../install.sh | ... bash` 的脚本配合 ADB 安装到电视上，README/issue 里维护着一张不断增长的「已验证机型」清单（索尼、康佳、PPTV、红米等陆续被社区补充验证）。项目用「桌面守护」机制保证开机后自动回到 Aerial，而不必停用原厂桌面；早期版本（1.9/1.10）的守护会拦截遥控按键导致部分电视变慢，作者在 1.11 起移除、1.14 做了进一步修复——从 issue 的往来能看到一个「两天内连发数个版本、快速响应真实机型反馈」的高强度迭代节奏。

它采用 MIT 许可，仓库体量不大但 issue 活跃（大量用户在报机型、报卡顿、要适配），本质是一个「社区驱动的机型适配 + 启动器体验」项目。

💡 可借鉴的优点

- **产品思维**：切中一个被广泛忍受但很少被正面解决的痛点——「电视首页太吵」。不做加法，而是用「安静、无广告、内容优先」做减法，定位清晰。
- **工程化**：用一条安装脚本 + ADB 把「刷机级」的改造降到普通用户也能操作；用「桌面守护」保证开机接管，又在发现它拖慢遥控响应后果断移除，体现了对真实设备性能的敏感。
- **社区运营**：把「已验证机型」做成公开、可追加的清单，把适配工作众包给用户，issue 既是支持渠道也是机型数据库——这是硬件适配类项目极高效的协作范式。
- **响应速度**：两天内连发多个版本修 bug、针对具体型号排查（要求用户贴 `dumpsys gfxinfo`、`top` 输出），工程诊断很务实。

🌟 特别亮眼的地方

aerial-tv 和紧随其后的 free-my-tv（#2）一起说明：**「把被厂商占领的屏幕还给用户」正在成为一个真实的开源赛道**。它最值得借鉴的，是如何用最轻的手段（脚本 + ADB + 众包机型清单）去啃「碎片化硬件适配」这块硬骨头——不追求一次性支持所有设备，而是建立一个「用户报机型→作者快速验证→清单增长」的正向循环，让社区本身成为适配引擎。

📖 项目是干什么的

REA-Prompts（REAP，即 Reverse Engineer Anything - Prompts）是一套用于「逆向任何东西」的提示词集合。它的目标是：借助大模型，把一个程序、一段逻辑或一个产品「拆开来看」——理解它怎么实现、抽出它的核心机制，甚至据此克隆或复刻其功能。

从仓库的极小体量（几十 KB、几乎没有代码）可以看出，它的价值不在软件本身，而在**「怎么问」**——把「逆向分析」这件原本高度依赖经验的工作，整理成一组结构化、可复用的提示词模板，让使用者对着任意目标套用这套提问框架，由 LLM 产出分析结论。标签标注为 prompt-engineering / rea / reverse-engineering，定位清楚。

需要说明的是，「逆向 / 克隆任意程序」天然带有版权与合规的灰色地带：它作为学习与分析方法论很有价值，但用于复刻受保护的商业软件则可能涉及法律风险。从技术产品角度看，它是「把专家工作流沉淀成提示词资产」这一趋势的又一个样本。

💡 可借鉴的优点

- **产品思维**：抓住「逆向分析门槛高、但人人想要」的痛点，把门槛从「懂汇编/调试」降到「会套提示词」，用 LLM 把专家能力平民化。
- **知识沉淀**：核心资产是一套「提问框架」而非代码——这提示我们，很多高价值工作流的护城河正在从「工具」转向「如何驱动通用模型去做这件事」。
- **轻量可复用**：几乎零依赖、纯文本，任何支持大模型的环境都能直接用，迁移成本极低。
- **结构化方法**：把发散的「逆向思路」整理成可按步骤执行的模板，本身就是一种可借鉴的知识管理方式。

🌟 特别亮眼的地方

REA-Prompts 热度的背后，是「提示词即资产」这一现象的延续：**当模型足够强，稀缺的不再是算力或模型，而是「把某个专业任务问清楚」的那套结构化提问方法。** 它和近期大量「XX-skill / XX-prompts」项目共同印证：垂直领域的 know-how 正在被封装成提示词或技能来分发。使用者在欣赏其方法论价值的同时，也要对「逆向/克隆」的版权边界保持清醒。

📖 项目是干什么的

fairplay-decrypt 做的是 iOS 安全研究里一个经典又硬核的课题：**离线解密 App Store 的 IPA**。苹果用 FairPlay DRM 对从商店下载的应用做加密，研究者要分析一个 App 的二进制，第一步往往就是「脱壳」（拿到解密后的可执行文件）。这个项目的卖点是**独立的密钥推导 + 离线解密**——不依赖在越狱设备上「运行时 dump」，而是自己把密钥算出来再解密。

用 C 实现、贴近底层，说明它直接和 Mach-O 可执行格式、FairPlay 的加密段打交道。相比传统「在设备上跑起来再从内存里抠」的 dump 方案，「离线 + 独立密钥推导」的路线理论上更干净、更可脚本化，也更利于在非设备环境（如分析服务器）批量处理。

这类工具的用途集中在**安全研究、恶意软件分析、App 审计**等正当场景，但同样处于版权与使用条款的敏感地带——解密受 DRM 保护的内容本身在很多司法辖区有法律约束，使用时需严格限定在授权研究范围内。

💡 可借鉴的优点

- **技术深度**：敢于碰 FairPlay 这种闭源 DRM，并走「独立密钥推导」而非「运行时 dump」的路线，是对加密实现理解到位的体现，含金量高。
- **工程取舍**：选择离线、不依赖越狱设备，换来了可脚本化、可批量、可在分析环境运行的工程优势——这是把「一次性 hack」做成「可用工具」的关键差别。
- **底层掌控**：用 C 直面 Mach-O 与加密段，没有多余抽象，适合作为学习 iOS 二进制结构与 DRM 机制的参考样本。
- **方法论价值**：对做移动安全的人，它示范了「与其在运行时碰运气，不如把密钥派生这件事从原理上解决」的思路。

🌟 特别亮眼的地方

它和今天榜上的 php2shell 系列（#5）一起，构成了「安全/逆向」这条副线。fairplay-decrypt 的启示在于：**真正耐用的安全工具，往往来自对加密/保护机制本身的深入理解，而不是对某个设备状态的临时利用。** 「独立密钥推导 + 离线处理」把一个依赖特定环境的操作变成了确定性的、可复现的流程——这正是安全工程里「从 exploit 到 tool」成熟化的标志。当然，它的强大也要求使用者守住法律与授权的边界。

📖 项目是干什么的

php2shell-poc 是围绕新披露的 **php2shell 漏洞（CVE-2026-109618 / CVE-2026-109619）**的一个安全研究仓库。它不只给出利用，而是提供了**多条 RCE（远程代码执行）利用链**，外加配套的**检测规则**——Suricata（IDS）、Sigma（通用检测规则）、ModSecurity（WAF 规则），把「怎么打」和「怎么防/怎么发现」放在了一起。

从标签看（php-exploit、rce、session-upload-progress、waf-rules、suricata-rules、detection-rules、wordpress-security 等），这组漏洞的核心是 PHP 的 **`session.upload_progress` 预认证（pre-auth）**攻击面——即无需登录即可触发的一类问题。本周 GitHub 上围绕同一组 CVE 出现了一批相关仓库（PoC、绕过 ASLR 的利用、官方/第三方的检测器等），ikow 这个是其中讨论度较高、内容相对完整的一个。

它采用 MIT 许可，面向的是**防守方与研究者**：拿利用链验证自己的系统是否受影响，拿检测规则接入自己的 IDS/WAF 来发现攻击。和所有漏洞 PoC 一样，它只应被用于授权测试与防御加固。

💡 可借鉴的优点

- **攻防一体**：不只发利用，还同时给 Suricata/Sigma/ModSecurity 三类检测规则——把「红队验证」和「蓝队防御」打包，极大提升了对防守方的实用价值。
- **工程化**：用 Python 把多条 RCE 链组织成可运行的 PoC，并以标准化的检测规则格式交付，方便直接接入现有安全栈。
- **响应速度**：在 CVE 披露后极短时间内就形成了「利用 + 检测」的完整材料，体现了安全社区围绕新漏洞快速协作的能力。
- **可对照性**：同一周多个同主题仓库并存（绕过 ASLR 的变体、官方 checker 等），为研究者提供了横向对比不同实现的机会。

🌟 特别亮眼的地方

这组 php2shell 仓库集中爆发，生动展示了**现代漏洞披露后的「社区响应曲线」**：PoC、变体利用、检测规则、官方校验器会在几天内围绕同一个 CVE 迅速聚集。对防守方的直接启示是——**新 CVE 出现时，第一时间要找的不只是补丁，还有可直接接入 IDS/WAF 的检测规则**；php2shell-poc「利用链 + 检测规则同仓交付」的做法，正是让防守方能最快受益的范式。前提永远是：仅在授权环境中使用。

📖 项目是干什么的

hatchzip 解决一个几乎人人遇到过、却很少有工具正面处理的尴尬：**解压一个巨大的压缩包时，磁盘根本放不下「压缩包 + 解压结果」两份数据**。它的巧思是「就地孵化」（extract in place）——一边解压、一边**把已经解出来的部分从源压缩包里删掉**，于是压缩包随着文件「孵化」出来而不断缩小，你只需要能装下**最终输出**的空间，而不是「输入 + 输出」两份。

它支持 ZIP、7z、tar 以及分卷（split）归档，用 Rust 实现、提供 CLI 和 GUI，并特别标注「crash-safe（崩溃安全）」——这是「边删边解压」这种危险操作的关键：一旦中途断电或崩溃，不能把源文件和已解出的数据一起毁掉。仓库标签里 disk-space、crash-safe、extract 等直指它的核心卖点。它采用 Apache-2.0 许可，并有独立主页（hatchzip.dev）。

对经常要在磁盘吃紧的服务器、笔记本上处理几十上百 GB 数据集、备份包、游戏资源的人来说，这类工具能直接把「必须先腾出两倍空间」的硬约束砍掉一半。

💡 可借鉴的优点

- **产品思维**：精准锁定一个「低频但极痛」的场景（磁盘不够解压大文件），用一个反直觉但有效的机制（边解边缩）去解，定位极其清晰。
- **工程化**：把「crash-safe」作为一等公民——因为「边删源文件边写新文件」本质上是在刀尖跳舞，崩溃恢复、事务性/原子性处理是它能否被信任的生命线。
- **架构设计**：统一支持 ZIP/7z/tar/分卷等多种格式，意味着它在「不同归档格式的流式读取 + 原地截断」上做了抽象，是有难度的底层工程。
- **可用性**：同时提供 CLI 和 GUI，照顾脚本化与普通用户两类人群；Rust 带来的内存安全对这种高风险文件操作尤为重要。

🌟 特别亮眼的地方

### #8 colinhacks/reylo ⭐

| 属性 | 信息 |
| --- | --- |

📖 项目是干什么的

reylo 来自 Zod 的作者 Colin McDonnell，解决 TypeScript 全栈开发里一个长期的摩擦点：**让你直接 `import` 一个 `.sql` 文件，并对其中的查询获得完整的类型推断——而且零代码生成（zero codegen）**。

传统上，要让手写 SQL 在 TS 里有类型，通常得靠 codegen：跑一个工具扫描你的 SQL、生成一堆 `.ts` 类型文件，再在代码里引用。这套流程的痛点是「需要构建步骤、生成物要维护、改一句 SQL 就要重新生成」。reylo 的目标是把这一切省掉——把 SQL 文件当成一等公民直接导入，类型在导入处自动「活」起来，无需额外的生成产物。它用 **Rust** 实现核心（解析 SQL、推断类型），对外表现为 TS 的导入能力，有独立主页（reylo.dev）、MIT 许可。

考虑到作者正是 Zod（TS 生态里最主流的 schema 校验库之一）的作者，reylo 可以看作他「用类型系统消灭样板代码」一贯理念在「SQL ↔ TS」这条缝上的延续。

💡 可借鉴的优点

- **产品思维**：瞄准 codegen 流程的核心痛点——「要构建步骤、要维护生成物」，用「直接 import + 零 codegen」把开发体验拉满，定位非常锋利。
- **架构设计**：用 Rust 做重活（SQL 解析 + 类型推断），把结果以最自然的「import .sql」形态暴露给 TS 开发者，是「底层高性能 + 上层极简 DX」的典型组合。
- **工程化**：零 codegen 意味着没有生成物漂移、没有「忘了重新生成」的坑，SQL 改了类型立刻跟着变，心智负担更低。
- **作者信誉**：出自 Zod 作者之手，在 TS 类型工程上的设计品味与社区号召力都有保证，值得关注其类型推断的实现细节。

🌟 特别亮眼的地方

reylo 代表了 TS 生态一个持续的追求：**把「类型安全」做到既强又无感——不靠额外的构建步骤，而是让类型「随源文件而活」。** 它和作者早年写的「让 monorepo 里的类型实时联动」一脉相承。对天天在 SQL 与 TS 之间来回的后端/全栈工程师，它给出的启示是：很多「类型 vs 便利」的取舍，其实可以靠更聪明的工具设计同时拿到——关键在于把复杂度藏进（Rust 写的）底层，给上层留一个干净的入口。

📖 项目是干什么的

ElyOffice（Ely Office）是一套用 **Rust + GPUI** 构建的**离线优先（offline-first）桌面办公应用**。它的两个关键词很明确：一是「离线优先」——不依赖云、数据在本地，强调隐私与可用性；二是技术栈选了 **GPUI**（Zed 编辑器团队开源的、以 GPU 渲染驱动的 Rust UI 框架），意味着它追求的是原生级的流畅与性能，而不是又一个 Electron 套壳。

用 GPUI 做办公套件是个颇有野心的选择：GPUI 以「用 GPU 画整个界面、追求极致响应」著称，常见于高性能编辑器场景；把它用到文档/表格这类复杂富交互的办公场景，是对这套 UI 框架能力边界的一次有趣探索。仓库体量不小（数万 KB）、MIT 许可、有项目主页（office.elygpui.com），从标签与定位看，它想做的是「本地、快、开源」的 Office 替代方向。

在 Web 化、云化席卷一切的今天，ElyOffice 代表了一股「回到本地原生」的逆流——把办公软件重新做成「你的数据在你机器上、界面快到没有延迟」的样子。

💡 可借鉴的优点

- **技术选型**：用 GPUI（GPU 驱动的 Rust UI）而非 Electron 来做办公套件，赌的是「原生性能 + 内存安全」，对追求流畅与低资源占用的桌面应用是一条值得关注的路线。
- **产品定位**：「离线优先 + 开源」直接回应了用户对云办公「隐私、锁定、要联网」的顾虑，是一个清晰的差异化卖点。
- **架构设计**：办公套件天然是富交互、强性能需求的复杂应用，用 Rust 兜住内存安全与性能、用 GPUI 兜住渲染，是面向复杂桌面 GUI 的一套现代组合。
- **生态示范**：它也在客观上扩展了 GPUI 的应用边界——证明这套框架不止能做编辑器，为后来者提供了参考。

🌟 特别亮眼的地方

当大多数新应用默认「上云、用 Web 技术、Electron 打包」时，ElyOffice 选择了几乎相反的路：**本地优先、Rust 原生、GPU 渲染。** 它的启示在于，「技术栈的默认选择」本身就是一种可以被挑战的产品决策——Electron 省事但重，云端方便但要联网且把数据交出去；而随着 Rust GUI 生态（GPUI 等）成熟，「做一个快、省、数据留在本地的原生桌面应用」重新变得可行。对关注桌面端、注重性能与隐私的开发者，ElyOffice 是观察「后 Electron 时代」桌面应用长什么样的一个很好的窗口。
